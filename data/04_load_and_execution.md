# 04. 부하 설정과 테스트 실행

## 적용 화면 또는 기능

본 문서는 Performance Station에서 성능테스트의 부하 조건을 설정하고 테스트를 실행·모니터링·중지하는 방법을 설명합니다.

주요 적용 화면 및 기능은 다음과 같습니다.

* 부하 설정 화면
* 시나리오별 부하 설정 화면
* VUser 설정 화면
* Ramp-up / Ramp-down 설정 화면
* Think Time 설정 화면
* 테스트 실행 화면
* 테스트 실행 제어 화면
* 실시간 모니터링 화면
* 테스트 중지 / 일시정지 기능
* Load Generator 상태 확인 화면

전체적인 흐름은 다음과 같습니다.

시나리오 및 스크립트 준비
→ 목표 부하 정의
→ VUser / TPS / Think Time 설정
→ Ramp-up 설정
→ 테스트 실행 전 점검
→ 테스트 실행
→ 실시간 모니터링
→ 테스트 종료
→ 결과 분석

---

# 부하 설정이란?

부하 설정은 Performance Station에서 얼마나 많은 사용자가, 어느 정도의 속도로, 얼마 동안 시스템을 사용하는 상황을 재현할 것인지 정의하는 과정입니다.

실제 서비스에서는 모든 사용자가 동시에 같은 업무를 수행하지 않습니다.

사용자는 화면을 조회하고, 내용을 읽고, 다음 버튼을 선택하기까지 일정한 시간을 소비합니다.

성능테스트에서는 이러한 실제 사용자 행동을 다음 항목을 이용하여 모델링합니다.

* Virtual User(VUser)
* TPS
* Think Time
* Ramp-up
* Ramp-down
* 테스트 지속시간
* 시나리오별 업무 비율

따라서 단순히 VUser 수를 크게 설정하는 것이 아니라 실제 운영 사용량을 최대한 유사하게 모델링하는 것이 중요합니다.

---

# 사전 조건

## 1. 목표 TPS 확인

부하를 설정하기 전에 대상 시스템이 처리해야 하는 목표 TPS를 정의합니다.

TPS(Transaction Per Second)는 일반적으로 1초 동안 처리되는 요청 또는 트랜잭션의 수를 의미합니다.

예:

목표 성능

104 TPS

라면 정상 운영 또는 Peak 상황에서 초당 약 104건의 업무를 처리할 수 있는지를 확인하는 형태로 테스트를 구성할 수 있습니다.

목표 TPS는 다음 자료를 기준으로 산정할 수 있습니다.

* 기존 운영 시스템의 Peak TPS
* 사용자 수
* 업무 처리 건수
* 시간대별 트래픽
* 신규 서비스 예상 사용자 수
* 시스템 용량계획
* 업무 담당자가 정의한 목표 성능

가능하면 단순 예상값보다는 실제 운영 데이터를 기반으로 목표 TPS를 설정하는 것을 권장합니다.

---

## 2. 대상 시스템 정보 확인

테스트를 실행하기 전에 대상 환경을 명확하게 확인합니다.

예:

* 개발계
* 검증계
* 성능계
* 운영 유사 환경
* 운영계

대상 시스템의 다음 정보도 확인합니다.

* 대상 URL
* 서버 IP
* WAS 구성
* DB 구성
* Load Balancer 구성
* 외부 연계 시스템
* 인증 시스템
* 대상 서버 CPU / Memory
* Network 구성

특히 검증 환경이 운영 환경보다 축소되어 있다면 테스트 결과를 해석할 때 해당 구성 차이를 반드시 고려해야 합니다.

---

## 3. Load Generator 상태 확인

Performance Station에서 실제 부하를 발생시키는 Load Generator가 정상적인 상태인지 확인합니다.

확인 항목:

* Load Generator 연결 상태
* CPU 사용률
* Memory 사용률
* Network 상태
* JMeter 실행 가능 여부
* 대상 시스템 접근 가능 여부

부하발생기의 자원이 부족하면 대상 시스템이 아니라 Load Generator 자체가 병목이 되어 정확한 테스트 결과를 얻지 못할 수 있습니다.

---

## 4. 시나리오와 스크립트 확인

부하 설정 전에 등록한 모든 시나리오가 정상적으로 실행되는지 확인합니다.

최소한 다음 조건을 만족하는 것이 좋습니다.

1 VUser 정상 실행
→ 소규모 VUser 정상 실행
→ 목표 부하 테스트

처음부터 수백 또는 수천 VUser를 적용하지 않는 것을 권장합니다.

---

## 5. 테스트 데이터 확인

다음 테스트 데이터가 충분히 준비되어 있는지 확인합니다.

* 로그인 계정
* 고객번호
* 계약번호
* 상품정보
* 업무 처리용 데이터

특히 로그인 세션이나 업무 데이터에 동시 사용 제한이 있는 경우 VUser 수에 맞는 충분한 테스트 데이터를 확보해야 합니다.

---

# 단계별 절차

# 1. VUser 설정

## VUser란?

VUser(Virtual User)는 성능테스트에서 실제 사용자의 행동을 가상으로 수행하는 사용자를 의미합니다.

예:

300 VUser

는 300명의 가상 사용자가 동시에 시스템을 사용하는 환경을 의미합니다.

하지만

300 VUser = 실제 사용자 300명

이라고 단순하게 해석해서는 안 됩니다.

실제 사용자는 요청을 보내고 일정 시간 화면을 확인한 뒤 다음 행동을 수행하기 때문입니다.

따라서 VUser는 Think Time과 함께 해석해야 합니다.

---

## VUser 설정 절차

1. Performance Station에서 대상 프로젝트를 선택합니다.
2. 실행할 테스트를 선택합니다.
3. 부하 설정 또는 Load 설정 화면으로 이동합니다.
4. 대상 시나리오를 선택합니다.
5. VUser 수를 입력합니다.
6. 시나리오별 VUser 또는 업무 비율을 설정합니다.
7. 설정값을 저장합니다.

예:

| 시나리오    | VUser | 업무 비율 |
| ------- | ----: | ----: |
| 고객조회    |   120 |   40% |
| 계약조회    |    90 |   30% |
| 보험료계산   |    60 |   20% |
| 해약환급금조회 |    30 |   10% |
| 합계      |   300 |  100% |

이처럼 실제 운영 업무 비율을 기준으로 VUser를 분배하는 것이 좋습니다.

---

# 2. Think Time 설정

## Think Time이란?

Think Time은 사용자가 하나의 요청을 처리한 후 다음 행동을 하기까지 대기하는 시간을 의미합니다.

예:

사용자 로그인

↓

고객정보 조회

↓

화면 내용 확인 30초

↓

계약조회

이 경우 30초가 Think Time에 해당합니다.

---

## Think Time이 중요한 이유

Think Time을 0으로 설정하면 VUser가 쉬지 않고 계속해서 요청을 발생시킵니다.

실제 사용자는 이런 방식으로 시스템을 사용하지 않기 때문에 비현실적으로 높은 부하가 발생할 수 있습니다.

예를 들어 같은 300 VUser라도 다음 두 조건의 부하는 크게 다릅니다.

조건 A

* 300 VUser
* Think Time 30초

조건 B

* 300 VUser
* Think Time 0초

조건 B가 훨씬 많은 요청을 발생시킵니다.

따라서 VUser 수만으로 부하 수준을 판단하면 안 됩니다.

---

## VUser와 실제 사용자 규모 이해

예를 들어 업무 특성을 분석했을 때 실제 사용자가 평균적으로 약 30초의 Think Time을 가진다면, Performance Station에서 사용하는 VUser는 전체 실제 사용자보다 작은 수로 운영 환경을 모델링할 수 있습니다.

예:

300 VUser + Think Time 30초

를 특정 업무 모델에서 약 3,000명의 실제 사용자 규모를 재현하기 위한 부하 모델로 정의할 수 있습니다.

같은 기준이라면

600 VUser + Think Time 30초

는 약 6,000명 수준의 사용자 규모를 가정한 부하 모델로 활용할 수 있습니다.

다만 이 환산값은 고정 공식이 아닙니다.

실제 업무의

* 요청 개수
* 응답시간
* 사용자 행동 패턴
* 시나리오 길이
* Think Time

에 따라 달라지므로 해당 시스템의 업무 모델을 기준으로 계산해야 합니다.

---

# 3. Ramp-up 설정

## Ramp-up이란?

Ramp-up은 테스트 시작 이후 설정한 VUser까지 사용자를 점진적으로 증가시키는 시간입니다.

예:

* 목표 VUser: 300
* Ramp-up: 300초

이라면 약 5분 동안 VUser가 단계적으로 증가하여 최종적으로 300 VUser에 도달하도록 구성할 수 있습니다.

---

## Ramp-up이 필요한 이유

처음부터 수백 명의 사용자를 동시에 투입하면 실제 운영 상황보다 급격한 트래픽이 발생할 수 있습니다.

또한 순간적인 부하 증가 때문에 다음 현상이 발생할 수 있습니다.

* Connection 급증
* Thread 급증
* CPU 순간 상승
* DB Connection Pool 고갈
* Session 생성 집중
* 인증 서버 부하
* Cache Warm-up 영향

따라서 일반적인 성능테스트에서는 사용자를 점진적으로 증가시키는 것이 좋습니다.

---

## Ramp-up 설정 예시

### 기준 부하 테스트

* VUser: 300
* Ramp-up: 10분
* 목표 부하 유지: 60분
* Ramp-down: 5분

흐름:

0 VUser
→ 10분 동안 증가
→ 300 VUser
→ 60분 유지
→ 5분 동안 감소
→ 테스트 종료

---

### 최대부하 테스트

최대부하 테스트에서는 단계적으로 부하를 증가시킬 수 있습니다.

예:

100 TPS

↓

200 TPS

↓

300 TPS

↓

400 TPS

↓

500 TPS

각 단계에서 다음 항목을 확인합니다.

* TPS 증가 여부
* 응답시간
* CPU
* Memory
* Error
* DB
* 외부 연계 시스템

부하는 증가하는데 TPS가 더 이상 증가하지 않고 응답시간과 오류율만 증가하기 시작한다면 시스템이 임계점에 접근했을 가능성이 있습니다.

---

# 4. Ramp-down 설정

Ramp-down은 테스트 종료 시 VUser를 점진적으로 감소시키는 시간입니다.

예:

* 300 VUser
* Ramp-down 5분

300
→ 250
→ 200
→ 150
→ 100
→ 50
→ 0

Ramp-down을 설정하면 실제 사용자가 점차 서비스를 종료하는 상황과 유사하게 테스트를 종료할 수 있습니다.

---

# 5. 테스트 지속시간 설정

테스트 목적에 따라 적절한 실행시간을 설정합니다.

예:

### 기능 및 스크립트 확인

약 5~10분

### 기준 부하 테스트

30분 ~ 1시간

### 최대부하 테스트

부하 단계별 10~30분

### 안정성 테스트

4시간 / 8시간 / 12시간 / 24시간 등

테스트 시간은 반드시 테스트 목적에 따라 결정합니다.

특히 안정성 테스트는 짧은 시간 동안 확인하기 어려운 다음 문제를 찾기 위해 장시간 수행합니다.

* Memory Leak
* Connection Leak
* 지속적인 응답시간 증가
* Resource 누적
* GC 문제
* Thread 증가
* 장시간 처리 오류

---

# 6. 테스트 실행 전 최종 확인

테스트 실행 버튼을 선택하기 전에 다음 사항을 확인합니다.

## 테스트 대상

* 올바른 서버를 대상으로 하고 있는가?
* 개발계 / 검증계 / 운영계를 잘못 선택하지 않았는가?
* URL이 올바른가?

## 부하 설정

* 목표 TPS가 올바른가?
* VUser가 올바른가?
* Ramp-up이 설정되어 있는가?
* Think Time이 올바른가?
* 테스트 시간이 올바른가?

## 시나리오

* 모든 시나리오가 정상 실행되는가?
* 업무 비율 합계가 정상인가?
* 스크립트 버전이 올바른가?

## 데이터

* 테스트 계정이 충분한가?
* 테스트 데이터가 충분한가?

## 모니터링

* WAS 모니터링이 연결되어 있는가?
* DB 모니터링이 가능한가?
* CPU / Memory 수집이 가능한가?
* 관계자가 테스트 시작을 인지하고 있는가?

---

# 7. 테스트 실행

모든 준비가 완료되면 Performance Station에서 테스트를 실행합니다.

일반적인 절차:

1. 프로젝트 선택
2. 테스트 선택
3. 부하 설정 확인
4. 시나리오 확인
5. Load Generator 상태 확인
6. 실행 버튼 선택
7. 최종 설정 확인
8. 테스트 시작

테스트가 시작되면 설정된 Ramp-up 조건에 따라 Virtual User가 증가합니다.

---

# 8. 실행 중 모니터링

테스트가 시작되면 Performance Station의 실시간 모니터링 화면에서 상태를 확인합니다.

단순히 테스트가 실행되고 있는지만 확인하지 않고 부하 발생 상태와 대상 시스템 상태를 함께 확인해야 합니다.

---

## 핵심 지표 1. TPS

실제 처리량을 확인합니다.

예:

목표

104 TPS

실제

106 TPS

라면 목표 처리량을 만족하고 있는지 확인할 수 있습니다.

다만 TPS만 만족한다고 테스트가 성공한 것은 아닙니다.

응답시간, 오류율 및 시스템 자원을 함께 확인해야 합니다.

---

## 핵심 지표 2. 응답시간

주요 업무별 응답시간을 확인합니다.

확인 항목:

* 평균 응답시간
* 최대 응답시간
* 필요 시 Percentile 응답시간
* 특정 시점의 응답시간 급증

예:

목표

평균 응답시간 1초 이하

실제

0.8초

라면 목표를 충족합니다.

---

## 핵심 지표 3. Error Rate

오류율을 확인합니다.

오류가 증가한다면 다음 항목을 확인합니다.

* HTTP Error
* Timeout
* 인증 실패
* 업무 Error
* Connection Error
* Script Error

단순한 서버 오류뿐 아니라 테스트 스크립트와 테스트 데이터 문제도 함께 확인해야 합니다.

---

## 핵심 지표 4. VUser

현재 실행 중인 Virtual User 수를 확인합니다.

Ramp-up이 정상적으로 수행되고 있는지 확인합니다.

예:

100 → 150 → 200 → 250 → 300 VUser

설정한 VUser까지 증가하지 않는다면 Load Generator 상태나 스크립트 오류를 확인합니다.

---

## 핵심 지표 5. CPU

WAS, DB 및 주요 서버의 CPU 사용률을 확인합니다.

예:

* WAS1 CPU
* WAS2 CPU
* DB CPU
* 인증 서버 CPU

CPU가 지속적으로 90~100%에 도달하는 경우 시스템 병목 가능성을 확인합니다.

다만 CPU 사용률만으로 시스템 병목을 판단하지 않습니다.

---

## 핵심 지표 6. Memory

Memory 사용량을 확인합니다.

특히 안정성 테스트에서는 시간에 따른 Memory 추세를 확인합니다.

정상적인 GC 이후 Memory가 일정 수준으로 회수되지 않고 지속적으로 증가한다면 Memory Leak 가능성을 분석합니다.

---

# 테스트 중 함께 확인해야 하는 시스템 지표

가능한 경우 다음 지표도 함께 확인합니다.

### WAS

* CPU
* Memory
* Heap
* Thread
* GC
* Connection Pool

### DB

* CPU
* Active Session
* Connection
* Slow Query
* Lock
* Wait

### Load Balancer

* Server 상태
* Connection
* Traffic 분배

### 외부 연계 시스템

* 응답시간
* Error
* Timeout

성능저하는 대상 WAS뿐만 아니라 외부 시스템의 병목으로도 발생할 수 있습니다.

# 정상적인 모니터링 예

예를 들어 다음 조건으로 테스트를 수행한다고 가정합니다.

목표

* 104 TPS
* 평균 응답시간 1초 이하
* CPU 80% 이하

실행 결과

* TPS: 108
* 평균 응답시간: 0.7초
* WAS1 CPU: 41%
* WAS2 CPU: 43%
* Error: 0%

이 경우 목표 부하를 안정적으로 처리하고 있다고 판단할 수 있습니다.

# 비정상 패턴 예시

다음과 같은 패턴이 발생한다면 추가 분석이 필요합니다.

### 부하는 증가하는데 TPS가 증가하지 않음

가능한 원인:

* WAS 병목
* DB 병목
* 외부 연계 병목
* Connection Pool 부족
* Thread Pool 부족

---

### TPS 하락 + 응답시간 급증

가능한 원인:

* 서버 임계점 도달
* DB 지연
* 외부 시스템 Timeout
* GC
* Network 문제

---

### CPU는 낮은데 응답시간이 증가

CPU가 낮다고 시스템에 문제가 없는 것은 아닙니다.

다음 항목을 확인합니다.

* DB
* 외부 연계
* Network
* Lock
* Connection Pool
* Thread 대기
* 인증 시스템

특히 외부 시스템의 응답이 느려진 경우 WAS CPU는 오히려 낮게 나타날 수도 있습니다.

# 9. 테스트 일시정지

Performance Station이 일시정지 기능을 제공하는 환경에서는 실행 중인 테스트를 일시정지할 수 있습니다.

일반적인 절차:

1. 실행 중인 테스트 선택
2. 일시정지(Pause) 선택
3. 현재 상태 확인
4. 필요 작업 수행
5. 재개(Resume) 선택

단, 일시정지는 시스템과 도구의 구현 방식에 따라 VUser 또는 세션 상태에 영향을 줄 수 있습니다.

따라서 중요한 공식 테스트에서는 일시정지 후 동일 테스트를 이어가는 것보다 상황에 따라 해당 실행을 종료하고 다시 수행하는 것이 결과 분석 측면에서 더 명확할 수 있습니다.

---

# 10. 테스트 중지

테스트 중 문제가 발생하거나 목적한 테스트 시간이 완료된 경우 테스트를 중지합니다.

일반적인 절차:

1. 실행 중인 테스트 선택
2. 중지(Stop) 선택
3. 중지 여부 확인
4. 실행 중인 VUser 종료 확인
5. 테스트 상태가 종료로 변경되는지 확인
6. 결과 데이터 저장 상태 확인

---

# 즉시 테스트 중지를 검토해야 하는 상황

다음 상황이 발생하면 테스트를 지속하기보다 중지를 검토합니다.

* 대상 시스템 서비스 장애
* 예상하지 못한 운영 시스템으로 부하 전송
* CPU 또는 Memory 임계 상태
* 오류율 급증
* 대량 Timeout
* DB 장애
* 외부 연계 시스템 장애
* 예상보다 과도한 TPS 발생
* 테스트 데이터로 실제 업무 데이터가 변경될 위험
* Load Generator 이상

---

# 테스트 중지 시 주의사항

## 브라우저를 종료하는 것과 테스트 중지는 다릅니다.

Performance Station에서 서버 측으로 부하를 발생시키는 경우 사용자가 브라우저 창을 닫더라도 테스트가 계속 실행될 수 있습니다.

따라서 테스트를 종료하려면 반드시 Performance Station의 중지 기능을 이용하여 실제 실행 상태를 확인합니다.

---

## 강제 종료는 가능한 한 피합니다.

테스트를 강제로 종료하면 다음 문제가 발생할 수 있습니다.

* 일부 결과 데이터 누락
* 진행 중 Transaction 미완료
* 세션 잔존
* 테스트 상태 불일치
* 결과 통계 왜곡

가능하면 정상적인 Stop 또는 Ramp-down 방식으로 종료합니다.

---

## 중간에 종료된 테스트는 별도로 표시합니다.

정상적으로 완료된 결과와 사용자가 중간에 종료한 결과를 동일하게 해석해서는 안 됩니다.

예:

상태: 중도 종료

중지 사유: DB 응답시간 급증

등과 같이 기록해 두는 것이 좋습니다.

---

# 부하 설정 시 주의사항

## 1. 처음부터 최대 부하를 적용하지 않습니다.

다음과 같이 단계적으로 부하를 증가시키는 것이 안전합니다.

1 VUser

↓

10 VUser

↓

소규모 부하

↓

목표 부하

↓

최대 부하

이 과정에서 스크립트와 시스템의 이상 여부를 먼저 확인합니다.

---

## 2. VUser와 TPS를 동일하게 생각하지 않습니다.

100 VUser = 100 TPS

가 아닙니다.

TPS는 다음 요소의 영향을 받습니다.

* VUser
* 응답시간
* Think Time
* 시나리오 길이
* Transaction 개수

따라서 목표 TPS를 만들기 위해 적절한 VUser와 Think Time을 산정해야 합니다.

---

## 3. Think Time을 무조건 0으로 설정하지 않습니다.

Think Time 0은 사용자가 쉬지 않고 연속해서 요청하는 환경입니다.

특별한 최대처리량 테스트 목적이 아니라면 실제 사용자 행동을 반영한 Think Time을 사용하는 것이 좋습니다.

---

## 4. Ramp-up을 너무 짧게 설정하지 않습니다.

짧은 시간 안에 많은 사용자를 투입하면 시스템이 정상적으로 Warm-up 되기도 전에 순간적인 부하가 발생합니다.

목표가 순간 부하 테스트가 아니라면 적절한 Ramp-up을 적용합니다.

---

## 5. 검증 환경과 운영 환경의 차이를 고려합니다.

검증계가 운영계보다 서버 수가 적다면 테스트 결과를 단순 비교해서는 안 됩니다.

예:

운영계

WAS 2대

검증계

WAS 1대

이 경우 검증계에서 발생한 병목이 운영계에서도 동일하게 발생한다고 단정하기 어렵습니다.

반대로 검증 환경에서 확인된 병목을 무조건 서버 수 비율로 단순 환산해서도 안 됩니다.

시스템 구조와 병목 지점을 함께 분석해야 합니다.

---

## 6. 운영 시스템에는 임의로 부하를 발생시키지 않습니다.

성능테스트는 짧은 시간에도 매우 큰 트래픽을 발생시킬 수 있습니다.

운영 환경에서 테스트가 필요한 경우 반드시 사전에 다음 사항을 협의합니다.

* 수행 시간
* 목표 TPS
* 최대 부하
* 영향 대상
* 모니터링 담당자
* 장애 발생 시 중지 기준
* 복구 절차

---

↓

WAS2 처리 확인

↓

서비스 정상화 확인

* Connection
* 서비스 중단시간

# 자주 발생하는 문제

## 설정한 TPS가 나오지 않습니다.

### 가능한 원인

* VUser 부족
* Think Time이 너무 김
* 응답시간 증가
* 대상 시스템 병목
* 외부 연계 시스템 병목
* Load Generator 성능 부족
* 테스트 스크립트 문제

### 조치

VUser만 바로 증가시키기보다 현재 응답시간, VUser 상태, 오류율 및 서버 자원을 먼저 확인합니다.

---

## VUser가 설정한 수까지 증가하지 않습니다.

### 가능한 원인

* 스크립트 Error
* Load Generator Resource 부족
* Ramp-up 설정 오류
* 사용자 계정 충돌
* 테스트 데이터 부족

### 조치

Load Generator와 스크립트 로그를 확인합니다.

---

## TPS가 갑자기 떨어집니다.

### 확인사항

* 응답시간 증가 여부
* Error 증가 여부
* CPU
* Memory
* GC
* DB 상태
* 외부 연계 시스템
* Network
* Connection Pool

TPS 하락 시 Performance Station의 부하 그래프와 서버 모니터링 정보를 동일한 시간대를 기준으로 비교하는 것이 중요합니다.

---

## CPU는 낮은데 성능이 좋지 않습니다.

CPU 사용률만으로 시스템 성능을 판단하지 않습니다.

다음을 확인합니다.

* DB 대기
* 외부 연계 지연
* Connection Pool
* Thread Pool
* Network
* Lock
* 인증 서버
* 외부 API

서버가 다른 시스템의 응답을 기다리고 있다면 CPU 사용률은 낮으면서 응답시간은 증가할 수 있습니다.

---

## 중지 버튼을 눌렀는데 바로 종료되지 않습니다.

실행 중인 Transaction 또는 VUser를 정상적으로 종료하는 과정에서 일정 시간이 필요할 수 있습니다.

강제 종료하기 전에 현재 실행 상태와 VUser 감소 여부를 확인합니다.
