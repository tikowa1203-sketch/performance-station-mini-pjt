# 07. 문제 해결 FAQ

## 적용 화면 또는 기능

본 문서는 Performance Station 사용 중 자주 발생할 수 있는 문제와 해결 방법을 정리한 FAQ 문서입니다.

주요 적용 화면 및 기능은 다음과 같습니다.

* 로그인 화면
* 메인 대시보드
* 프로젝트 목록 화면
* 프로젝트 생성/수정 화면
* 테스트 생성/수정 화면
* 시나리오 관리 화면
* JMeter 스크립트 업로드 화면
* 스크립트 검증 화면
* 테스트 데이터 관리 화면
* 부하 설정 화면
* Load Generator 상태 화면
* 테스트 실행/중지 화면
* 실시간 모니터링 화면
* 테스트 결과 조회 화면
* 보고서 생성/다운로드 화면
* 사용자 및 권한 관리 화면

본 문서는 사용자가 문제가 발생했을 때 다음 순서로 확인할 수 있도록 구성합니다.

증상 확인
→ 가능한 원인 확인
→ 기본 환경 확인
→ Performance Station 설정 확인
→ 스크립트/데이터 확인
→ 대상 시스템 확인
→ 조치
→ 필요 시 관리자 문의

---

## 사전 조건

없음.

문제가 발생하면 먼저 화면에 표시되는 다음 정보를 확인하고 가능한 경우 캡처 또는 기록합니다.

* 오류 메시지
* 오류 코드
* 발생 시간
* 프로젝트명
* 테스트명
* 사용자 ID
* 실행한 기능
* 사용한 스크립트 버전
* 대상 환경
* 테스트 실행 ID 또는 결과 ID

이 정보가 있으면 문제 원인을 훨씬 빠르게 찾을 수 있습니다.

# FAQ 1. Performance Station에 로그인이 되지 않습니다.

## 증상

* 로그인 버튼을 눌러도 접속되지 않음
* 인증 실패 메시지가 표시됨
* ID 또는 Password 오류가 표시됨
* 로그인 후 다시 로그인 화면으로 이동함

## 가능한 원인

* ID 또는 Password 오류
* 계정 미등록
* 계정 잠금
* 사용자 권한 미부여
* SSO 인증 오류
* VPN 또는 사내망 미접속
* 인증 서버 장애
* Performance Station 서비스 장애

## 확인 순서

1. ID와 Password를 다시 확인합니다.
2. 사내망 또는 VPN 연결 상태를 확인합니다.
3. 다른 사내 시스템 로그인이 정상인지 확인합니다.
4. 다른 사용자의 Performance Station 접속 여부를 확인합니다.
5. 계정이 Performance Station에 등록되어 있는지 확인합니다.
6. 반복적인 로그인 실패로 계정이 잠기지 않았는지 확인합니다.

## 조치 방법

* ID 또는 Password를 다시 입력합니다.
* VPN 또는 사내망에 다시 연결합니다.
* 브라우저를 재실행하거나 다른 지원 브라우저로 접속합니다.
* 계정 잠금 시 관리자에게 잠금 해제를 요청합니다.
* 다수 사용자가 동시에 로그인하지 못한다면 Performance Station 또는 인증 시스템 상태를 확인합니다.

---

# FAQ 2. 로그인은 되는데 메뉴가 보이지 않습니다.

## 증상

* 프로젝트 생성 메뉴가 없음
* 테스트 생성 버튼이 없음
* 실행 버튼이 비활성화됨
* 사용자 관리 메뉴가 표시되지 않음

## 가능한 원인

대부분 사용자 권한과 관련된 문제입니다.

* 일반 조회 권한만 부여됨
* 프로젝트 관리 권한 없음
* 테스트 실행 권한 없음
* 관리자 권한 없음
* 프로젝트별 권한 미부여

## 확인 순서

1. 현재 로그인한 계정을 확인합니다.
2. 사용자 권한 레벨을 확인합니다.
3. 해당 프로젝트의 참여 사용자로 등록되어 있는지 확인합니다.
4. 필요한 기능에 대한 권한이 부여되어 있는지 확인합니다.

## 조치 방법

시스템 관리자 또는 프로젝트 관리자에게 필요한 권한을 요청합니다.

예:

프로젝트 조회 권한은 있으나 테스트 실행 권한이 없어 실행 버튼이 비활성화되어 있습니다.

---

# FAQ 3. 프로젝트가 목록에 보이지 않습니다.

## 증상

다른 사용자는 프로젝트를 볼 수 있지만 본인의 프로젝트 목록에는 표시되지 않습니다.

## 가능한 원인

* 프로젝트 접근 권한 미부여
* 프로젝트 참여자로 등록되지 않음
* 검색 필터 적용
* 종료된 프로젝트 숨김
* 다른 조직 또는 프로젝트 그룹으로 등록
* 프로젝트가 삭제 또는 비활성화됨

## 확인 순서

1. 프로젝트 검색어를 초기화합니다.
2. 상태 필터를 전체로 변경합니다.
3. 프로젝트가 실제 존재하는지 다른 사용자에게 확인합니다.
4. 프로젝트 참여자 목록에 본인 계정이 있는지 확인합니다.
5. 접근 권한을 확인합니다.

## 조치 방법

프로젝트 관리자에게 사용자를 프로젝트 참여자로 등록하고 필요한 권한을 부여하도록 요청합니다.

---

# FAQ 4. 프로젝트 생성 버튼이 보이지 않습니다.

## 증상

프로젝트 목록은 조회되지만 신규 프로젝트를 만들 수 없습니다.

## 가능한 원인

프로젝트 생성 권한이 없는 사용자일 가능성이 높습니다.

## 확인 순서

1. 사용자 권한을 확인합니다.
2. 프로젝트 생성 권한이 별도로 필요한지 확인합니다.
3. 관리자 계정에서는 버튼이 표시되는지 확인합니다.

## 조치 방법

관리자에게 프로젝트 생성 권한을 요청합니다.

---

# FAQ 5. 테스트 생성 버튼이 비활성화되어 있습니다.

## 가능한 원인

* 테스트 생성 권한 부족
* 프로젝트 접근 권한 부족
* 프로젝트가 종료 상태
* 프로젝트 필수정보 미입력
* 프로젝트가 잠금 상태

## 확인 순서

1. 프로젝트 상태를 확인합니다.
2. 프로젝트 필수정보가 모두 등록되어 있는지 확인합니다.
3. 사용자 권한을 확인합니다.
4. 다른 사용자도 동일한 문제가 있는지 확인합니다.

## 조치 방법

프로젝트 상태를 정상으로 변경하거나 테스트 생성 권한을 요청합니다.

---

# FAQ 6. JMeter 스크립트 업로드가 되지 않습니다.

## 증상

* JMX 업로드 실패
* 지원하지 않는 파일이라는 메시지 표시
* 파일을 선택해도 등록되지 않음
* 업로드 중 오류 발생

## 가능한 원인

* 지원하지 않는 파일 형식
* JMX 파일 손상
* 파일 용량 초과
* 파일명에 특수문자 포함
* JMeter 버전 호환 문제
* 업로드 권한 부족

## 확인 순서

1. 파일 확장자가 `.jmx`인지 확인합니다.
2. 로컬 JMeter에서 정상적으로 열리는지 확인합니다.
3. 파일 크기를 확인합니다.
4. 파일명을 단순하게 변경하여 재시도합니다.
5. 지원 JMeter 버전을 확인합니다.
6. 업로드 권한을 확인합니다.

## 조치 방법

로컬 JMeter에서 정상 실행되는 JMX를 다시 저장하고 업로드합니다.

예:

`customer_search_v1.2.jmx`

와 같이 버전이 명확한 파일명을 사용하는 것을 권장합니다.

---

# FAQ 7. 로컬 JMeter에서는 정상인데 Performance Station에서 실행되지 않습니다.

## 증상

개인 PC에서 JMeter 테스트는 정상이나 Performance Station에서는 스크립트 오류 또는 실행 실패가 발생합니다.

## 가능한 원인

가장 흔한 원인은 실행 환경 차이입니다.

* JMeter 버전 차이
* Plugin 미설치
* Java 버전 차이
* 로컬 파일 경로 사용
* Load Generator에서 대상 시스템 접근 불가
* 인증서 또는 Proxy 차이
* 환경변수 차이

## 확인 순서

1. Performance Station의 JMeter 버전을 확인합니다.
2. 사용 중인 Plugin을 확인합니다.
3. CSV 및 외부 파일 경로를 확인합니다.
4. `C:\...`와 같은 로컬 절대경로가 있는지 확인합니다.
5. Load Generator에서 대상 URL에 접근 가능한지 확인합니다.
6. 인증서 또는 Proxy 설정을 확인합니다.

## 조치 방법

가능하면 기본 JMeter 기능을 사용하고 외부 Plugin 의존성을 최소화합니다.

로컬 경로는 상대경로 또는 Performance Station에서 지원하는 데이터 파일 관리 방식으로 변경합니다.

---

# FAQ 8. CSV 파일을 찾을 수 없다는 오류가 발생합니다.

## 증상

* File Not Found
* CSV Data Set Config 오류
* 테스트 데이터가 읽히지 않음

## 가능한 원인

JMeter 스크립트가 로컬 PC의 파일 경로를 참조하고 있을 가능성이 높습니다.

잘못된 예:

`C:\Users\user\Desktop\users.csv`

## 확인 순서

1. JMX의 CSV Data Set Config를 확인합니다.
2. CSV 경로를 확인합니다.
3. Performance Station에 CSV가 등록되어 있는지 확인합니다.
4. 파일명 대소문자를 확인합니다.
5. 상대경로 사용 여부를 확인합니다.

## 조치 방법

CSV 파일을 Performance Station에 함께 등록하고 지원되는 경로 방식으로 변경합니다.

---

# FAQ 9. 로그인 요청은 성공하지만 이후 요청부터 실패합니다.

## 증상

로그인 API는 정상이나 고객조회, 계약조회 등 다음 요청부터 인증 오류가 발생합니다.

## 가능한 원인

* Session 미전달
* Cookie 미전달
* Token 추출 실패
* Correlation 실패
* JWT 만료
* Header 설정 누락

## 확인 순서

1. 로그인 응답에 Session 또는 Token이 있는지 확인합니다.
2. JMeter Extractor가 해당 값을 정상 추출하는지 확인합니다.
3. Debug Sampler 등을 이용하여 변수값을 확인합니다.
4. 다음 요청의 Header / Cookie를 확인합니다.
5. Token 만료시간을 확인합니다.

## 조치 방법

JSON Extractor, Regular Expression Extractor 등의 Correlation 설정을 확인하고 후속 요청에 추출한 값을 전달합니다.

---

# FAQ 10. HTTP 200인데 테스트는 실패로 표시됩니다.

## 가능한 원인

HTTP 통신 자체는 성공했지만 업무 처리가 실패했을 수 있습니다.

예:

```text
HTTP 200

{
  "result": "FAIL",
  "message": "고객 정보가 존재하지 않습니다."
}
```

또는 Assertion 조건과 실제 응답이 일치하지 않을 수 있습니다.

## 확인 순서

1. 실제 Response Body를 확인합니다.
2. 업무 성공/실패 코드를 확인합니다.
3. Assertion 조건을 확인합니다.
4. 테스트 데이터가 유효한지 확인합니다.

## 조치 방법

HTTP Code만으로 성공 여부를 판단하지 않고 업무 성공값을 기준으로 Assertion을 구성합니다.

---

# FAQ 11. VUser가 설정한 수까지 올라가지 않습니다.

## 증상

300 VUser로 설정했지만 150 또는 200 수준에서 더 이상 증가하지 않습니다.

## 가능한 원인

* Load Generator 자원 부족
* 스크립트 오류
* 로그인 계정 충돌
* 테스트 데이터 부족
* Ramp-up 설정 오류
* Thread 생성 실패
* JMeter 또는 Java Resource 부족

## 확인 순서

1. 현재 VUser 그래프를 확인합니다.
2. Load Generator CPU / Memory를 확인합니다.
3. JMeter 로그를 확인합니다.
4. Error Rate를 확인합니다.
5. 로그인 및 테스트 데이터 중복 여부를 확인합니다.
6. Ramp-up 값을 확인합니다.

## 조치 방법

Load Generator 병목인 경우 부하발생기를 확장하거나 분산 실행을 검토합니다.

스크립트 오류가 있다면 대규모 테스트를 중지하고 소규모 VUser부터 다시 검증합니다.

---

# FAQ 12. 목표 TPS가 나오지 않습니다.

## 증상

목표는 300 TPS인데 실제 결과는 200 TPS 수준에 머뭅니다.

## 가능한 원인

* VUser 부족
* Think Time이 너무 김
* 응답시간 증가
* WAS 병목
* DB 병목
* 외부 연계 병목
* Load Generator 병목
* 테스트 데이터 또는 스크립트 오류

## 확인 순서

다음 순서로 확인합니다.

① VUser
→ ② Think Time
→ ③ 응답시간
→ ④ Error
→ ⑤ Load Generator
→ ⑥ WAS
→ ⑦ DB
→ ⑧ 외부 연계

## 조치 방법

VUser를 바로 증가시키지 말고 현재 시스템의 응답시간과 병목 여부를 먼저 확인합니다.

시스템이 이미 임계점에 도달한 상태에서 VUser만 증가시키면 TPS는 증가하지 않고 응답시간과 오류율만 증가할 수 있습니다.

---

# FAQ 13. 부하를 올렸는데 TPS는 더 이상 증가하지 않습니다.

## 증상

예:

* 300 VUser → 300 TPS
* 400 VUser → 390 TPS
* 500 VUser → 400 TPS
* 600 VUser → 395 TPS

## 가능한 원인

시스템이 최대 처리 한계에 접근했을 가능성이 있습니다.

## 확인 순서

동일 시간대의 다음 지표를 확인합니다.

* 응답시간
* Error Rate
* CPU
* Memory
* DB
* Connection Pool
* Thread
* 외부 시스템

## 조치 방법

TPS가 정체되는 시점과 동시에 증가한 자원 또는 대기 지표를 찾아 병목 구간을 분석합니다.

VUser를 계속 증가시키는 것보다 병목 원인을 찾는 것이 우선입니다.

---

# FAQ 14. TPS가 갑자기 떨어집니다.

## 가능한 원인

* 응답시간 급증
* Timeout
* DB 지연
* 외부 시스템 지연
* GC
* 서버 장애
* 네트워크 문제
* Load Generator 문제
* 테스트 데이터 고갈

## 확인 순서

TPS 하락이 시작된 정확한 시간을 확인합니다.

같은 시간대의

* VUser
* 응답시간
* Error

# FAQ 16. CPU가 100%에 가까워집니다.

## 가능한 원인

* 실제 CPU 병목
* 지나치게 높은 부하
* 과도한 Thread
* GC
* 특정 로직의 CPU 사용 증가
* 암호화/복호화 처리
* 비정상 반복 처리

## 확인 순서

1. 부하 증가 시점과 CPU 상승 시점을 비교합니다.
2. TPS가 계속 증가하는지 확인합니다.
3. 응답시간이 증가하는지 확인합니다.
4. GC를 확인합니다.
5. Thread와 Application 로그를 확인합니다.

## 조치 방법

CPU가 지속적으로 90~100%이고 TPS는 증가하지 않으며 응답시간이 상승하면 CPU 병목 가능성을 검토합니다.

필요 시 부하를 낮추거나 테스트를 중지하고 상세 분석합니다.

# FAQ 17. Memory 사용량이 계속 증가합니다.

## 가능한 원인

* 정상적인 Heap 증가
* GC 주기 문제
* Memory Leak
* Session 누적
* Cache 증가
* Object 미회수

## 확인 순서

Memory 절대값만 보지 않고 시간에 따른 패턴을 확인합니다.

정상적인 예:

40% → 60% → GC → 42% → 60% → GC → 43%

주의가 필요한 예:

40% → 60% → GC → 50% → 70% → GC → 60% → 80%

## 조치 방법

GC 이후의 기준 Memory가 지속적으로 상승한다면 Heap Dump, GC Log 등의 추가 분석을 검토합니다.

특히 안정성 테스트에서는 수 시간 동안의 추세를 확인합니다.

# FAQ 22. 브라우저를 닫았는데 테스트가 계속 실행됩니다.

## 조치 방법

Performance Station에 다시 접속하여 해당 테스트의 실행 상태를 확인하고 중지(Stop) 기능으로 종료합니다.

브라우저 종료를 테스트 중지 방법으로 사용하지 않습니다.

# FAQ 28. 최대 TPS는 높게 나왔는데 평균 TPS가 낮습니다.

## 가능한 원인

순간적으로 높은 처리량이 발생했지만 전체 테스트 구간에서는 해당 수준이 지속되지 않았기 때문입니다.

예:

* 최대 TPS: 500
* 평균 TPS: 350

이 경우 500 TPS가 순간적으로만 발생했을 수 있습니다.

## 확인 순서

1. TPS 그래프를 시간대별로 확인합니다.
2. 500 TPS가 얼마나 오래 유지되었는지 확인합니다.
3. 같은 시점의 응답시간과 Error를 확인합니다.

## 조치 방법

순간 최대 TPS를 시스템의 안정적인 최대 처리량으로 사용하지 않습니다.

일정 시간 안정적으로 유지된 처리량을 기준으로 판단합니다.

# FAQ 29. CPU가 50%인데 부하를 두 배 올려도 되나요?

## 답변

CPU 50%라는 이유만으로 부하를 두 배까지 올릴 수 있다고 판단하면 안 됩니다.

시스템 성능은 다음 요소의 영향을 함께 받습니다.

* DB
* Connection Pool
* Thread Pool
* Network
* 외부 연계
* 인증 시스템
* Lock

CPU와 TPS가 항상 비례하는 것은 아닙니다.

## 권장 방법

부하를 단계적으로 증가시키면서 다음을 함께 확인합니다.

TPS + 응답시간 + 오류율 + CPU + Memory + DB + 외부 연계

---

# FAQ 30. WAS를 2대로 늘리면 TPS도 두 배가 되나요?

## 답변

반드시 그렇지는 않습니다.

WAS가 병목이고 시스템이 수평 확장에 적합한 구조라면 처리량 증가를 기대할 수 있습니다.

하지만 다음 공유 자원이 병목이라면 WAS를 늘려도 TPS가 두 배로 증가하지 않을 수 있습니다.

* DB
* 외부 API
* 인증 시스템
* Cache
* Network
* Storage

따라서 서버 증설 효과는 실제 테스트를 통해 확인해야 합니다.

---

한 건의 최대값만으로 전체 성능을 실패라고 판단하지 않지만, 반복적으로 발생한다면 원인 분석이 필요합니다.

# 문제 해결 기본 원칙

Performance Station에서 문제가 발생하면 다음 순서로 확인하는 것을 권장합니다.

① 오류 메시지를 확인한다.
→ ② 문제가 특정 사용자만 발생하는지 확인한다.
→ ③ 프로젝트/권한 문제인지 확인한다.
→ ④ 스크립트 문제인지 확인한다.
→ ⑤ 테스트 데이터 문제인지 확인한다.
→ ⑥ Load Generator 문제인지 확인한다.
→ ⑦ 대상 WAS/DB 문제인지 확인한다.
→ ⑧ 외부 연계 시스템 문제인지 확인한다.
→ ⑨ 발생 시점의 로그와 모니터링 데이터를 비교한다.

특히 성능테스트 문제는 하나의 시스템에서만 발생하지 않을 수 있습니다.

Performance Station
→ Load Generator
→ Network
→ WAS
→ DB
→ 외부 연계 시스템

전체 요청 경로를 기준으로 문제 구간을 좁혀가는 것이 중요합니다.

---

# 가장 먼저 기억해야 할 문제 해결 원칙

프로젝트가 안 보인다
→ 권한과 필터부터 확인

스크립트가 안 된다
→ 1 VUser로 재현

로컬에서는 되고 Performance Station에서는 안 된다
→ 실행 환경 차이 확인

TPS가 안 나온다
→ VUser부터 무조건 늘리지 않기

CPU가 낮은데 느리다
→ DB/외부 연계/대기 자원 확인

TPS가 떨어진다
→ 동일 시간대의 응답시간·Error·CPU·DB 비교

Error가 발생한다
→ 시스템 오류인지 스크립트/데이터 오류인지 먼저 구분

Memory가 증가한다
→ 순간값보다 GC 이후 장기 추세 확인

브라우저를 닫았다
→ 테스트가 종료됐다고 생각하지 않기

최대 TPS가 높다
→ 그 값이 얼마나 오래 안정적으로 유지됐는지 확인
