# 05. 결과 확인과 보고서

## 적용 화면 또는 기능

본 문서는 Performance Station에서 완료된 성능테스트의 결과를 조회하고, 주요 성능지표를 분석한 뒤 보고서를 다운로드하는 방법을 설명합니다.

주요 적용 화면 및 기능은 다음과 같습니다.

* 테스트 결과 목록 화면
* 테스트 결과 상세 화면
* 성능지표 대시보드
* TPS / 처리량 그래프
* 응답시간 그래프
* 오류율 / 오류 상세 화면
* 시스템 자원 모니터링 화면
* WAS / DB / 서버 자원 조회 화면
* 테스트 결과 비교 화면
* 보고서 생성 화면
* 보고서 다운로드 메뉴

일반적인 결과 확인 흐름은 다음과 같습니다.

테스트 종료
→ 결과 데이터 수집 완료 확인
→ 테스트 결과 조회
→ TPS 확인
→ 응답시간 확인
→ 오류율 확인
→ 서버 자원 확인
→ 시간대별 지표 비교
→ 병목 여부 판단
→ 테스트 결과 정리
→ 보고서 생성 및 다운로드

---

# 사전 조건

## 1. 결과 조회 권한

테스트 결과를 조회하려면 해당 프로젝트 또는 테스트에 대한 조회 권한이 필요합니다.

일반적으로 다음과 같은 사용자가 결과를 조회할 수 있습니다.

* 시스템 관리자
* 프로젝트 관리자
* 성능테스트 담당자
* 프로젝트 참여 사용자
* 결과 조회 권한이 부여된 사용자

프로젝트는 조회되지만 테스트 결과가 보이지 않는 경우 다음 사항을 확인합니다.

* 해당 프로젝트에 접근 권한이 있는지
* 테스트 결과 조회 권한이 있는지
* 프로젝트 참여자로 등록되어 있는지
* 조회 필터가 적용되어 있는지

---

## 2. 테스트 실행 상태 확인

결과를 정상적으로 조회하려면 테스트가 종료되어 있어야 합니다.

대표적인 테스트 상태는 다음과 같습니다.

* 대기
* 준비
* 실행 중
* 완료
* 중도 종료
* 실패

테스트가 실행 중인 경우 실시간 데이터는 확인할 수 있지만 최종 결과와 보고서는 아직 생성되지 않을 수 있습니다.

따라서 최종 결과를 분석할 때는 테스트 상태가 완료 또는 결과 수집이 완료된 상태인지 확인합니다.

---

## 3. 결과 데이터 수집 완료 확인

테스트가 종료된 직후에는 일부 모니터링 데이터나 통계 데이터가 아직 집계 중일 수 있습니다.

확인 항목:

* TPS 데이터 수집 완료
* 응답시간 집계 완료
* 오류 데이터 수집 완료
* 서버 자원 데이터 수집 완료
* 보고서 생성 가능 상태

테스트 종료 직후 그래프 일부가 비어 있다면 데이터 수집 상태를 먼저 확인합니다.

# 단계별 절차

# 1. 테스트 결과 조회

## STEP 1. 프로젝트 선택

Performance Station에 로그인한 후 결과를 확인할 프로젝트를 선택합니다.

예:

영업지원시스템 성능검증

---

## STEP 2. 테스트 목록 이동

프로젝트 상세 화면에서 테스트 목록, 테스트 관리, 결과 조회 등의 메뉴로 이동합니다.

테스트 목록에서 다음 정보를 확인할 수 있습니다.

* 테스트명
* 테스트 유형
* 테스트 실행일
* 실행시간
* 상태
* 담당자
* 결과 조회 여부

---

## STEP 3. 확인할 테스트 선택

분석할 테스트를 선택합니다.

예:

영업지원_기준성능_1차

테스트 상세 화면에서 다음과 같은 결과를 확인할 수 있습니다.

* 테스트 실행 조건
* VUser
* 목표 TPS
* 실제 TPS
* 응답시간
* 오류율
* CPU / Memory
* 테스트 시작 / 종료 시간
* 시나리오별 처리 결과

---

## STEP 4. 테스트 조건 먼저 확인

결과를 보기 전에 테스트 조건을 먼저 확인합니다.

예:

* 목표 TPS: 104 TPS
* VUser: 300
* Think Time: 30초
* Ramp-up: 10분
* 테스트 시간: 60분
* 대상 환경: 검증계

테스트 조건을 확인하지 않고 결과값만 보면 잘못된 판단을 할 수 있습니다.

특히 서로 다른 테스트 결과를 비교할 때는 반드시 다음 조건이 동일하거나 유사한지 확인합니다.

* VUser
* Think Time
* 시나리오
* 업무 비율
* 대상 서버
* 대상 환경
* 스크립트 버전
* 테스트 데이터

# 2. 주요 지표 확인 방법

성능테스트 결과는 하나의 지표만 보고 판단하지 않습니다.

다음 지표를 함께 확인해야 합니다.

TPS

* 응답시간
* 오류율
* CPU
* Memory
* DB / 외부 연계 상태

---

# TPS 확인

## TPS란?

TPS(Transaction Per Second)는 초당 처리되는 트랜잭션 또는 요청의 수를 의미합니다.

예:

104 TPS

는 시스템이 초당 약 104건의 요청 또는 업무를 처리하고 있다는 의미입니다.

---

## TPS 확인 방법

Performance Station의 결과 대시보드에서 다음 정보를 확인합니다.

* 평균 TPS
* 최대 TPS
* 시간대별 TPS
* 시나리오별 TPS
* 목표 TPS 대비 실제 TPS

예:

목표 TPS

104 TPS

실제 평균 TPS

108 TPS

이 경우 처리량 자체는 목표를 만족한 것으로 볼 수 있습니다.

하지만 응답시간과 오류율을 함께 확인해야 합니다.

---

# TPS 해석 시 주의사항

TPS가 높다고 반드시 성능이 좋은 것은 아닙니다.

예:

결과 A

* TPS: 110
* 평균 응답시간: 0.8초
* Error: 0%

결과 B

* TPS: 115
* 평균 응답시간: 8초
* Error: 10%

TPS만 보면 결과 B가 더 좋아 보이지만 실제 서비스 품질은 결과 A가 더 안정적일 가능성이 높습니다.

따라서 TPS는 응답시간과 오류율을 함께 확인해야 합니다.

---

# 응답시간 확인

## 응답시간이란?

사용자가 요청을 보낸 시점부터 시스템이 응답을 완료할 때까지 걸린 시간을 의미합니다.

주요 확인 항목:

* 평균 응답시간
* 최소 응답시간
* 최대 응답시간
* 시나리오별 응답시간
* 시간대별 응답시간
* Percentile 응답시간

---

## 평균 응답시간

전체 요청의 평균 처리시간을 의미합니다.

예:

평균 응답시간 0.8초

목표가 1초 이하라면 평균 기준으로 목표를 만족합니다.

---

## 최대 응답시간

테스트 중 가장 느렸던 요청을 확인할 수 있습니다.

예:

평균 응답시간

0.8초

최대 응답시간

2.75초

평균 응답시간은 정상이어도 특정 시점 또는 특정 업무에서 응답시간이 크게 증가할 수 있으므로 최대 응답시간도 확인합니다.

---

## Percentile 응답시간

가능한 경우 평균뿐 아니라 Percentile 지표도 확인하는 것이 좋습니다.

예:

* P90
* P95
* P99

P95 응답시간이 2초라는 의미는 전체 요청의 약 95%가 2초 이내에 처리되었다는 의미로 해석할 수 있습니다.

평균값은 일부 매우 느린 요청이나 빠른 요청의 영향을 받을 수 있으므로 Percentile 값을 함께 보면 사용자 체감 성능을 보다 정확하게 판단할 수 있습니다.

---

# 응답시간 증가 패턴 확인

시간대별 그래프를 확인하여 응답시간이 특정 시점부터 증가했는지 확인합니다.

예:

10:00

0.7초

10:10

0.8초

10:20

1.2초

10:30

3.5초

이와 같은 패턴이 나타난다면 같은 시간대의 다음 지표를 함께 확인합니다.

* TPS
* VUser
* CPU
* Memory
* DB
* Error
* 외부 연계 시스템

성능 분석에서는 같은 시간대의 여러 지표를 함께 비교하는 것이 중요합니다.

---

# 오류율 확인

## 오류율이란?

전체 요청 중 정상적으로 처리되지 않은 요청의 비율입니다.

예:

전체 요청

100,000건

오류

100건

오류율

0.1%

---

## 확인해야 하는 오류

대표적으로 다음 오류를 확인합니다.

* HTTP 4xx
* HTTP 5xx
* Timeout
* Connection Error
* 인증 실패
* Session 오류
* 업무 오류
* Assertion 실패
* JMeter 스크립트 오류

---

## HTTP 200도 업무 오류일 수 있음

HTTP 응답 코드가 200이라고 해서 반드시 정상 처리된 것은 아닙니다.

예:

```text
HTTP 200

{
  "result": "FAIL",
  "message": "고객 정보가 존재하지 않습니다."
}
```

따라서 HTTP Code뿐 아니라 실제 업무 성공 여부를 확인하는 것이 중요합니다.

---

# 오류율 해석

오류가 발생하면 먼저 오류 원인을 분류합니다.

### 시스템 오류

예:

* HTTP 500
* DB 오류
* Connection Timeout
* WAS 오류

### 테스트 데이터 오류

예:

* 존재하지 않는 고객번호
* 잘못된 사용자 계정
* 중복 데이터

### 스크립트 오류

예:

* Correlation 실패
* Token 추출 실패
* Parameter 오류

성능 문제와 스크립트 문제를 구분해야 정확한 분석이 가능합니다.

---

# CPU 사용률 확인

CPU는 서버의 처리 부하를 판단하는 대표적인 지표입니다.

확인 대상:

* WAS1
* WAS2
* DB
* 인증 서버
* 외부 연계 서버

예:

WAS1 평균 CPU

41%

WAS2 평균 CPU

43%

이 경우 CPU 기준으로는 여유가 있는 것으로 볼 수 있습니다.

---

# CPU 해석 시 주의사항

CPU가 낮다고 반드시 시스템에 여유가 있는 것은 아닙니다.

예:

* TPS 감소
* 응답시간 증가
* CPU 30%

이 경우 다음 병목을 확인할 수 있습니다.

* DB 응답 지연
* 외부 연계 지연
* Thread 대기
* Connection Pool 부족
* Lock
* Network
* 인증 시스템

서버가 외부 시스템의 응답을 기다리는 동안 CPU는 낮게 나타날 수 있습니다.

---

# Memory 확인

Memory는 특히 장시간 수행하는 안정성 테스트에서 중요합니다.

확인 항목:

* Heap 사용량
* 전체 Memory
* GC
* 시간에 따른 Memory 증가
* GC 이후 Memory 회수 여부

---

## 정상적인 Memory 패턴

예:

사용량 증가
→ GC
→ Memory 감소
→ 다시 증가
→ GC

이와 같은 일정한 패턴이 반복될 수 있습니다.

---

## 비정상적인 Memory 패턴

예:

40%
→ 50%
→ GC
→ 48%
→ 60%
→ GC
→ 58%
→ 70%

GC가 수행되어도 기준 Memory가 계속 증가한다면 Memory Leak 가능성을 검토합니다.

# 지표를 함께 보는 방법

성능테스트 결과 분석에서 가장 중요한 것은 지표 간 상관관계입니다.

---

## 패턴 1. 정상 처리

* TPS 일정
* 응답시간 일정
* Error 거의 없음
* CPU 안정
* Memory 안정

판단:

목표 부하를 안정적으로 처리하는 상태

---

## 패턴 2. 시스템 임계점 접근

* VUser 증가
* TPS 증가
* CPU 증가
* 응답시간 증가

어느 시점 이후

* VUser 계속 증가
* TPS 증가하지 않음
* 응답시간 급증
* Error 증가

판단:

시스템이 처리할 수 있는 임계점에 접근했을 가능성

---

## 패턴 3. 외부 시스템 병목

* TPS 감소
* 응답시간 증가
* WAS CPU 낮음
* WAS Memory 정상

외부 연계 응답시간 증가

판단:

WAS 자체보다 외부 연계 시스템 병목 가능성

---

## 패턴 4. DB 병목

* TPS 증가 정체
* 응답시간 증가
* WAS CPU 중간 수준
* DB CPU 또는 DB Wait 증가
* Connection 증가

판단:

DB 구간의 병목 가능성

---

## 패턴 5. Memory 문제

장시간 테스트 중

* TPS 점진적 감소
* 응답시간 증가
* Memory 지속 상승
* GC 빈도 증가

판단:

Memory Leak 또는 GC 영향 가능성

---

# 목표 성능 충족 여부 판단

테스트 수행 전에 정의한 목표를 기준으로 결과를 판단합니다.

예:

## 목표

* 목표 TPS: 104 TPS 이상
* 평균 응답시간: 1초 이하
* 오류율: 1% 이하
* CPU: 80% 이하

## 실제 결과

* 평균 TPS: 110 TPS
* 평균 응답시간: 0.8초
* 오류율: 0.02%
* WAS CPU: 65%

## 판단

목표 성능 충족

이처럼 성능테스트 결과는 가능한 한 사전에 정의한 기준을 기반으로 판단합니다.

---

# 최대부하 테스트 결과 해석

최대부하 테스트는 어느 수준까지 시스템이 안정적으로 처리할 수 있는지 확인하는 것이 목적입니다.

예:

| 부하  | TPS | 응답시간 | CPU | Error |
| --- | --: | ---: | --: | ----: |
| 100 | 100 | 0.5초 | 25% |    0% |
| 200 | 200 | 0.7초 | 40% |    0% |
| 300 | 300 | 0.9초 | 55% |    0% |
| 400 | 398 | 1.3초 | 70% |  0.1% |
| 500 | 420 | 4.5초 | 88% |    8% |

이 경우 500 수준의 부하를 적용했지만 실제 TPS는 420 수준에서 정체되고 응답시간과 오류율이 급격히 증가했습니다.

따라서 시스템의 안정적인 처리 범위는 400 TPS 전후로 판단하고 병목 구간을 추가로 분석할 수 있습니다.

# 안정성 테스트 결과 해석

안정성 테스트에서는 특정 시점의 최대값보다 시간에 따른 변화 추세가 중요합니다.

예:

8시간 테스트 동안 다음 항목을 확인합니다.

* TPS가 일정하게 유지되는가?
* 응답시간이 증가하지 않는가?
* 오류가 누적되지 않는가?
* Memory가 지속적으로 증가하지 않는가?
* Connection이 회수되는가?
* Thread가 누적되지 않는가?

장시간 테스트의 핵심은 처음과 마지막의 상태가 유사하게 유지되는지 확인하는 것입니다.

---

# 가용성 테스트 결과 해석

가용성 테스트에서는 장애 발생 전·중·후의 지표를 비교합니다.

예:

정상 상태

TPS 300

↓

WAS1 장애

TPS 270

응답시간 일시 증가

↓

WAS2 단독 처리

TPS 300 회복

↓

WAS1 복구

TPS 300 유지

이 경우 확인할 항목:

* 장애 시 서비스 중단 여부
* TPS 하락 폭
* 응답시간 증가
* Error 발생량
* 정상 서버의 CPU 증가
* 전환 시간
* 복구 이후 정상화 시간

단순히 장애 서버가 다시 올라왔는지만 보는 것이 아니라 서비스 품질이 얼마나 빨리 정상 상태로 회복되었는지 확인합니다.

# 테스트 결과 비교

동일한 테스트를 여러 차수 수행한 경우 결과를 비교하는 것이 좋습니다.

예:

| 항목      |   1차 |   2차 |  변화 |
| ------- | ---: | ---: | --: |
| TPS     |  350 |  420 | +70 |

| CPU     |  80% |  65% |  감소 |
| Error   |   2% | 0.1% |  개선 |

이러한 비교를 통해 시스템 개선 또는 설정 변경 효과를 확인할 수 있습니다.

# 결과 비교 시 반드시 동일해야 할 조건

두 테스트를 비교하기 전에 다음 조건을 확인합니다.

* 시나리오
* 스크립트 버전
* VUser
* Think Time
* 업무 비율
* 테스트 데이터
* 서버 구성
* DB 구성
* 대상 환경

조건이 다르면 단순 수치 비교가 의미 없을 수 있습니다.

---

# 주의사항

## 1. 평균값만 보고 판단하지 않습니다.

평균 응답시간이 정상이어도 특정 요청에서 매우 긴 지연이 발생할 수 있습니다.

따라서 다음 지표를 함께 확인합니다.

* 평균
* 최대
* Percentile
* 시간대별 그래프

---

## 2. CPU만으로 성능을 판단하지 않습니다.

CPU가 50%라고 해서 시스템이 50%의 성능 여유를 가지고 있다고 단정할 수 없습니다.

병목은 다음 구간에서 발생할 수도 있습니다.

* DB
* Network
* Connection Pool
* Thread
* 외부 연계
* 인증 시스템

---

## 3. 서버 수만으로 성능을 단순 비례 계산하지 않습니다.

예:

WAS 1대에서 500 TPS가 나왔다고 해서

WAS 2대에서 반드시 1,000 TPS가 나온다고 단정할 수 없습니다.

실제 성능은 다음 요소의 영향을 받습니다.

* DB
* 외부 연계
* Load Balancer
* Network
* Session
* Shared Resource

서버 확장 가능성을 판단할 때는 시스템 구조를 함께 분석해야 합니다.

---

## 4. Peak 값만 보고 최대 성능으로 판단하지 않습니다.

테스트 중 순간적으로 500 TPS가 발생했다고 해서 시스템이 안정적으로 500 TPS를 처리할 수 있다고 판단하면 안 됩니다.

최대 처리 성능은 일정 시간 동안 다음 조건이 함께 유지되는지를 확인해야 합니다.

* TPS 유지
* 응답시간 안정
* Error 허용 범위
* 자원 사용률 안정

---

## 5. 중도 종료 테스트를 정상 완료 결과와 동일하게 보지 않습니다.

중간에 Stop한 테스트는 테스트 시간이 짧거나 Ramp-up 구간만 포함될 수 있습니다.

따라서 정상 완료 테스트와 비교할 때 중지 시점과 테스트 구간을 반드시 확인합니다.

---

## 6. 테스트 환경과 운영 환경의 차이를 기록합니다.

예:

운영계

WAS 2대 / DB 운영 구성

검증계

WAS 1대 / 외부 연계 일부 Mock

이 경우 결과 보고서에 환경 차이를 명확하게 기록합니다.

환경 차이를 기록하지 않으면 테스트 결과가 실제 운영 성능을 그대로 의미하는 것으로 오해될 수 있습니다.

---

## 7. Mock 연계 여부를 확인합니다.

외부 시스템을 Mock으로 처리한 경우 실제 운영 환경보다 응답시간이 빠르게 나타날 수 있습니다.

따라서 결과 보고서에 반드시 다음 내용을 기록합니다.

예:

통합인증 구간은 Mock 응답을 사용함

이를 통해 테스트 범위와 결과 해석의 한계를 명확하게 합니다.

---

## 8. 보고서 다운로드 권한을 확인합니다.

사용자 권한에 따라 다음 기능이 제한될 수 있습니다.

* 보고서 생성
* PDF 다운로드
* Excel 다운로드
* 원본 데이터 다운로드

다운로드 버튼이 보이지 않거나 비활성화되어 있는 경우 결과 조회 권한과 보고서 다운로드 권한을 확인합니다.

---

## 9. 보고서 생성 전 데이터 집계를 확인합니다.

테스트 종료 직후 보고서를 생성하면 일부 모니터링 데이터가 아직 반영되지 않을 수 있습니다.

결과 데이터 수집이 완료되었는지 확인한 뒤 보고서를 생성합니다.

---

# 자주 발생하는 문제

## 테스트 결과가 보이지 않습니다.

### 가능한 원인

* 테스트가 아직 실행 중
* 결과 집계 중
* 사용자 권한 부족
* 프로젝트 접근 권한 없음
* 조회 기간 필터 적용

### 조치

테스트 상태, 프로젝트 권한 및 검색 조건을 확인합니다.

---

## TPS 그래프가 중간에 떨어집니다.

### 확인사항

같은 시점의 다음 지표를 확인합니다.

* VUser
* 응답시간
* Error
* CPU
* Memory
* DB
* 외부 시스템

TPS 그래프 하나만으로 원인을 판단하지 않습니다.

---

## CPU는 정상인데 응답시간이 느립니다.

### 가능한 원인

* DB 병목
* 외부 시스템 지연
* Network
* Connection Pool
* Thread 대기
* Lock

### 조치

WAS CPU 이외의 지표를 같은 시간대를 기준으로 분석합니다.

---

## 결과가 이전 테스트보다 나빠졌습니다.

### 먼저 확인할 사항

* 테스트 조건이 동일한가?
* 스크립트 버전이 동일한가?
* 테스트 데이터가 동일한가?
* 서버 구성 변경이 있었는가?
* 배포 또는 설정 변경이 있었는가?
* 외부 연계 상태가 동일한가?

조건이 다르면 성능 저하라고 바로 판단하지 않습니다.

---

## 보고서 다운로드가 되지 않습니다.

### 가능한 원인

* 보고서 생성 권한 부족
* 테스트 결과 집계 미완료
* 팝업 차단
* 다운로드 차단
* 보고서 생성 오류

### 조치

브라우저 다운로드 설정과 사용자 권한을 확인합니다.

---

# 결과 분석 권장 순서

Performance Station에서 성능테스트 결과를 분석할 때 다음 순서로 확인하는 것을 권장합니다.

① 테스트 조건 확인
→ ② 목표 TPS 확인
→ ③ 실제 TPS 확인
→ ④ 응답시간 확인
→ ⑤ 오류율 확인
→ ⑥ 시간대별 그래프 확인
→ ⑦ WAS CPU / Memory 확인
→ ⑧ DB 및 외부 연계 확인
→ ⑨ 병목 구간 분석
→ ⑩ 목표 성능 충족 여부 판단
→ ⑪ 이전 테스트와 비교
→ ⑫ 결과 보고서 작성

단순히 숫자가 높고 낮은지를 보는 것이 아니라 동일 시간대의 지표가 어떻게 함께 움직였는지 확인하는 것이 성능 분석의 핵심입니다.
