# 성능검증 표준 가이드

## 목표 정의

* 성능검증의 목표는 단순히 높은 TPS를 확인하는 것이 아니라 예상 운영 부하에서 서비스가 요구 수준의 처리량, 응답시간, 안정성 및 가용성을 유지할 수 있는지 검증하는 것이다.

* 목표 TPS는 다음 정보를 근거로 산정한다.

  * 일/월 최대 업무 처리량
  * 피크 시간대 업무량
  * 피크 집중률
  * 업무별 발생 비중
  * 사용자 증가율
  * 향후 서비스 성장률
  * 시스템 여유율
  * 기존 운영 시스템의 Peak TPS
  * 신규 시스템의 예상 업무량

* 목표 TPS를 산정할 때 평균 업무량만 사용하지 않고 실제 운영에서 발생할 수 있는 Peak 시간대의 집중 현상을 반영한다.

* 필요 시 현재 운영 부하뿐 아니라 예상 성장률과 여유율을 추가하여 목표를 설정한다.

예:

`현재 Peak 80 TPS × 성장률 1.2 × 여유율 1.1 ≒ 106 TPS`

→ 목표 TPS를 약 104~110 TPS 수준으로 설정할 수 있다.

---

### VUser 산정

동시사용자 환산의 기본적인 관계는 다음과 같이 이해할 수 있다.

`VUser ≈ TPS × (평균 응답시간 + Think Time)`

반대로 TPS는 다음과 같이 단순 추정할 수 있다.

`TPS ≈ VUser ÷ (평균 응답시간 + Think Time)`

예:

* 평균 응답시간: 1초
* Think Time: 3초
* VUser: 300

이라면

`300 ÷ (1 + 3) = 약 75 TPS`

이다.

반대로 동일 조건에서 104 TPS를 재현하려면

`104 × (1 + 3) = 약 416 VUser`

가 필요하다.

단, 이 공식은 하나의 사용자 반복 사이클을 하나의 Transaction으로 보는 단순화된 모델이다.

실제 시나리오에는 여러 Transaction, Timer, 호출 간격, 업무 비중 등이 포함되므로 최종 VUser는 사전 테스트를 통해 보정해야 한다.

---

### VUser 산정 시 고려사항

VUser는 실제 서비스 가입자 수나 전체 사용자 수와 동일하지 않다.

다음을 함께 고려한다.

* 실제 동시접속 사용자
* 사용자당 업무 수행 빈도
* Think Time
* 평균 응답시간
* 시나리오 내 Transaction 수
* 업무별 실행 비율
* 로그인 후 세션 유지시간
* 사용자 행동 패턴

따라서

`300 VUser = 실제 사용자 300명`

으로 단순 해석하지 않는다.

서비스 특성에 따라 수천 명의 실제 사용자 활동이 수백 VUser 수준으로 모델링될 수도 있다.

---

### 업무별 부하 모델

여러 업무를 동시에 테스트하는 경우 전체 TPS만 맞추지 않고 실제 운영 업무 비중을 반영한다.

예:

전체 목표: 200 TPS

* 고객조회: 40% → 80 TPS
* 계약조회: 30% → 60 TPS
* 보험료계산: 20% → 40 TPS
* 해약환급금조회: 10% → 20 TPS

업무 비율이 실제 운영과 크게 다르면 동일한 전체 TPS라 하더라도 DB, WAS, 외부 연계에 발생하는 부하 특성이 달라질 수 있다.

---

### 테스트 전 목표 정의 항목

성능테스트를 시작하기 전에 최소한 다음 항목을 정의한다.

* 대상 시스템
* 대상 환경
* 테스트 목적
* 목표 TPS
* 업무별 TPS
* VUser
* Think Time
* Ramp-up
* 부하 유지시간
* 응답시간 목표
* 허용 오류율
* CPU / Memory 기준
* 대상 서버 구성
* 외부 연계 포함 여부
* Mock 사용 여부
* 테스트 데이터 조건

통과 기준은 테스트가 끝난 후 정하지 않고 테스트 수행 전에 정의하는 것을 원칙으로 한다.

---

### 판정 원칙

통과 여부는 처리량 하나만으로 판단하지 않는다.

다음 네 가지 축을 함께 확인한다.

처리량

* 응답시간
* 오류율
* 시스템 자원

필요한 경우 다음 항목도 함께 확인한다.

* DB 상태
* Connection Pool
* Thread Pool
* GC
* Network
* 외부 연계 시스템
* Load Generator
* Queue
* Lock / Wait

성능검증의 핵심은 높은 TPS 자체가 아니라 요구한 TPS를 서비스 품질 저하 없이 안정적으로 처리하는지 확인하는 것이다.

---

## 권장 판정 기준

### 목표 처리량

* 목표 TPS 이상을 일정한 안정 구간에서 유지해야 한다.
* Ramp-up 중 순간적으로 목표 TPS를 기록한 것은 목표 달성으로 판단하지 않는다.
* 순간 최대 TPS보다 안정적으로 유지 가능한 처리량을 중요하게 본다.

예:

목표 104 TPS인 경우

* 순간 최대: 130 TPS
* 안정 구간 평균: 106 TPS
* 오류율: 0.05%
* 응답시간 정상

이라면 목표 처리량을 충족한 것으로 판단할 수 있다.

반대로

* 순간 최대: 130 TPS
* 안정 구간 평균: 90 TPS

라면 순간 최대치만으로 목표를 충족했다고 판단하지 않는다.

---

### 안정 구간 정의

성능 판정에 사용하는 구간은 Ramp-up 및 Ramp-down을 제외하고 부하가 일정하게 유지되는 Steady State 구간을 원칙으로 한다.

예:

* Ramp-up: 10분
* 부하 유지: 60분
* Ramp-down: 5분

이라면 주요 성능 판정은 가운데 60분의 안정 구간을 기준으로 한다.

Cache Warm-up, JVM Warm-up 등의 초기 영향을 고려하여 안정 구간의 시작점을 별도로 지정할 수도 있다.

---

### 응답시간

기본 예시는 다음과 같이 설정할 수 있다.

* 평균 응답시간: 1초 이하
* 개별 최대 응답시간: 3초 이하

단, 실제 판정은 해당 시스템의 SLA 또는 업무 특성을 우선한다.

예:

* 단순 조회: 1초 이하
* 복잡한 계약 계산: 3초 이하
* 대용량 조회: 5초 이하

와 같이 업무별 목표를 다르게 정의할 수 있다.

가능하면 평균 응답시간뿐 아니라 다음도 함께 확인한다.

* P90
* P95
* P99
* 최대 응답시간

---

### Percentile 활용

평균 응답시간만으로 사용자 체감 성능을 판단하지 않는다.

예:

* 평균: 0.8초
* P95: 1.4초
* 최대: 2.5초

라면 대다수 사용자가 안정적인 응답을 경험한 것으로 볼 수 있다.

반면

* 평균: 0.8초
* P95: 5초
* 최대: 20초

라면 평균은 동일하더라도 상당수 사용자에게 지연이 발생하고 있을 가능성이 있다.

따라서 서비스 중요도가 높은 경우 P95 또는 P99 기준을 SLA에 포함하는 것을 권장한다.

---

### 오류율

기본 예시는

0.1% 이하

를 사용할 수 있다.

단순 오류율만 확인하지 않고 오류를 다음과 같이 분류한다.

#### 시스템 오류

* HTTP 5xx
* DB 오류
* Connection 오류
* Timeout
* 서버 내부 오류

#### 업무 오류

* 잘못된 테스트 데이터
* 존재하지 않는 고객번호
* 중복 업무 처리
* 업무 검증 오류

#### 부하 도구 / 스크립트 오류

* Correlation 실패
* Parameter 오류
* JMeter Assertion 오류
* CSV 데이터 부족
* Load Generator 오류

스크립트 또는 테스트 데이터 오류를 시스템 성능 오류에 그대로 포함하지 않도록 구분한다.

---

### CPU

CPU는 지속적인 사용률을 기준으로 판단한다.

권장 예시:

평균 또는 안정구간 지속 CPU 70% 이하

다만 70%는 절대적인 합격/불합격 기준이 아니라 시스템 특성과 운영 정책에 따라 달라질 수 있다.

다음과 같은 순간적인 상승만으로 실패를 판정하지 않는다.

`50% → 순간 85% → 다시 55%`

반면

`75% → 85% → 95% → 지속 95% 이상`

이면서 TPS가 정체되고 응답시간이 증가한다면 CPU 병목 가능성을 검토한다.

---

### Memory

Memory는 단순 사용률보다 시간에 따른 변화와 GC 이후 회수 여부를 확인한다.

정상적인 패턴:

`40% → 60% → GC → 42% → 61% → GC → 43%`

주의가 필요한 패턴:

`40% → 60% → GC → 50% → 70% → GC → 61% → 80%`

GC 이후 기준 Memory가 지속적으로 증가하면 다음을 확인한다.

* Memory Leak
* Session 누적
* Cache 증가
* Object 미회수
* Connection 누수

---

### 안정성

안정성 테스트는 일반적으로 목표 또는 최대 안정 처리 부하의 약 70% 이상에서 수행한다.

권장 예:

* 부하 수준: 기준 처리량의 70% 이상
* 수행시간: 8시간 이상

다음 항목을 시간대별로 확인한다.

* TPS 유지 여부
* 응답시간 증가 여부
* 오류 누적 여부
* Memory 증가
* GC 증가
* Connection 누적
* Thread 증가
* CPU 변화

안정성 테스트에서는 순간 최대값보다 시간이 지나도 초기 성능이 유지되는가를 중요하게 본다.

---

### 목표 충족 예시

목표:

* 104 TPS
* 평균 응답시간 1초 이하
* 오류율 0.1% 이하
* CPU 70% 이하

결과:

* 안정 구간 TPS: 108 TPS
* 평균 응답시간: 0.8초
* P95: 1.3초
* 오류율: 0.02%
* WAS 평균 CPU: 42%

판정:

목표 성능 충족

단, 실제 운영 환경과 검증 환경의 구성 차이는 별도로 명시한다.

---

## 테스트 유형

### 1. 단위 성능

개별 업무 또는 API의 기본 처리 성능을 확인한다.

주요 목적:

* 특정 Transaction 응답시간 확인
* API 처리량 확인
* SQL 또는 API 개선 효과 확인
* 단일 업무의 병목 분석

일반적인 수행 흐름:

1 VUser 검증
→ 소규모 부하
→ 단계적 부하 증가

주요 확인 항목:

* TPS
* 평균/P95 응답시간
* 오류율
* CPU
* DB Query
* 외부 API

단위 성능 테스트에서는 복합 업무보다 특정 기능의 성능 특성을 분리하여 확인하는 것이 목적이다.

---

### 2. 최대 부하

시스템이 병목에 도달하기 전까지 안정적으로 처리할 수 있는 최대 한계를 찾는다.

권장 방식:

`100 TPS  
→ 200 TPS  
→ 300 TPS  
→ 400 TPS  
→ 500 TPS`

와 같이 부하를 단계적으로 증가시킨다.

각 단계에서 다음을 확인한다.

* 실제 TPS 증가 여부
* 응답시간 증가
* Error 증가
* CPU
* Memory
* DB
* Connection Pool
* Thread
* 외부 연계

다음과 같은 패턴이 나타나면 임계점에 접근했을 가능성이 있다.

부하는 증가
→ VUser 증가
→ TPS 증가 정체
→ 응답시간 급증
→ 오류 증가

최대부하의 결과값은 순간 최대 TPS가 아니라 안정적으로 유지 가능한 최대 처리량을 기준으로 한다.

---

### 최대부하 종료 기준

다음 상황에서는 추가적인 부하 증가를 중단하거나 테스트 중지를 검토한다.

* TPS가 더 이상 증가하지 않음
* 응답시간이 급격히 증가
* 오류율 급증
* CPU 지속 90~100%
* DB Connection 고갈
* 외부 시스템 장애 발생
* 서비스 영향 발생
* 테스트 환경의 안전 기준 초과

무조건 시스템이 장애 날 때까지 부하를 올리는 방식은 권장하지 않는다.

---

### 3. 안정성

장시간 동일한 부하를 유지하면서 성능이 저하되지 않는지 확인한다.

주요 목적:

* Memory Leak 확인
* Connection Leak 확인
* GC 문제 확인
* Thread 누적 확인
* 장시간 응답시간 증가 확인
* 오류 누적 확인

예:

최대 안정 처리량의 70% 수준 × 8시간

다음과 같이 초반·중반·후반 결과를 비교한다.

| 지표     |   초반 |    중반 |    후반 |
| ------ | ---: | ----: | ----: |
| TPS    |  300 |   301 |   298 |
| 응답시간   | 0.8초 |  0.8초 |  0.9초 |
| Memory |  45% |   47% |   46% |
| Error  |   0% | 0.01% | 0.01% |

이처럼 장시간 일정한 상태가 유지되는지 확인한다.

---

### 4. 가용성

서버 장애 또는 구성요소 장애 발생 시 서비스가 지속될 수 있는지 확인한다.

예:

WAS1 + WAS2 정상

↓

WAS1 중단

↓

WAS2 단독 처리

↓

WAS1 재기동

↓

정상 이중화 복구

주요 확인 항목:

* 장애 발생 시 서비스 중단 여부
* 세션 유지 여부
* TPS 감소
* 응답시간 증가
* Error 발생
* 정상 서버 CPU 증가
* Load Balancer 전환
* 복구 시간
* 재기동 서버 투입 시 영향

가용성 테스트에서는 단순히 장애 서버가 다시 살아났는지만 확인하지 않는다.

장애 전 → 장애 발생 → 전환 → 단독 운영 → 복구 → 정상화

전 구간의 서비스 품질을 확인한다.

---

### 가용성 판정 시 중요사항

WAS 1대가 중단되었을 때 남은 서버가 정상적으로 요청을 처리하더라도 다음을 함께 확인한다.

* TPS가 얼마나 감소했는가?
* 응답시간이 얼마나 증가했는가?
* Error가 발생했는가?
* Session이 손실되었는가?
* 정상 서버 CPU가 임계점에 도달했는가?
* 장애 서버 재투입 시 부하가 정상 재분배되는가?

특히 서버 복구 직후 다음 현상을 확인한다.

* Cache Warm-up
* Connection 재생성
* Session 재분배
* 순간적인 응답시간 증가
* TPS 감소

---

## 결과 판정 원칙

### 1. 하나의 지표만으로 판정하지 않는다.

성능 결과는 다음을 종합해서 판단한다.

TPS

* 응답시간
* 오류율
* CPU / Memory
* DB
* 외부 연계
* Load Generator

예:

TPS가 목표를 만족하더라도

* 응답시간이 과도하게 증가하거나
* 오류율이 높거나
* CPU가 지속적인 임계 상태라면

안정적으로 목표를 충족했다고 판단하기 어렵다.

---

### 2. 관측 사실과 해석을 분리한다.

보고서에서는 다음 세 단계를 구분한다.

#### 관측 사실

예:

* 450 TPS 부하부터 실제 TPS가 390~400 수준에서 정체됨
* 평균 응답시간이 0.9초에서 3.8초로 증가함
* WAS CPU는 평균 45% 수준으로 유지됨

#### 가설

예:

WAS CPU가 낮은 상태에서 TPS가 정체되었으므로 WAS CPU 외 구간의 병목 가능성이 있음.

#### 확인 방법

다음 항목을 추가 확인한다.

* DB Wait
* Slow Query
* 외부 연계 응답시간
* Connection Pool
* Thread Pool
* Network
* Load Generator

근거 없이

“DB가 병목이다.”

처럼 단일 원인을 확정하지 않는다.

---

### 3. 자원 사용률이 낮은데 TPS가 정체되는 경우

CPU 사용률이 낮다고 시스템에 충분한 여유가 있다고 판단하지 않는다.

다음 순서로 확인한다.

① 오류율
→ ② 응답시간
→ ③ DB
→ ④ 외부 연계
→ ⑤ Connection Pool
→ ⑥ Thread Pool
→ ⑦ Lock / Wait
→ ⑧ Network
→ ⑨ Load Generator

서버가 다른 시스템의 응답을 기다리는 상태라면 CPU는 오히려 낮게 나타날 수 있다.

---

### 4. 검증 환경과 운영 환경을 구분한다.

검증계가 운영계보다 축소 구성이라면 검증 환경에서 나타난 한계를 그대로 운영 시스템의 최대 성능으로 정의하지 않는다.

예:

운영계:

* WAS 2대
* DB 운영 구성
* 외부 연계 실서버

검증계:

* WAS 1대
* DB 축소 구성
* 외부 연계 일부 Mock

이 경우 보고서에는 다음을 구분하여 기록한다.

확인된 사실

검증 환경에서는 약 400 TPS 수준부터 처리량 증가가 정체됨.

환경적 제약

검증 환경이 운영 환경보다 축소되어 있음.

판단

해당 결과는 검증 환경에서 확인된 처리 한계이며 운영 환경의 절대 최대 성능을 의미하지 않음.

---

### 5. Mock 사용 여부를 반드시 기록한다.

외부 연계를 Mock으로 처리하면 실제 운영 환경과 다른 성능 특성이 나타날 수 있다.

예:

실제 인증 시스템:

평균 응답시간 200ms

Mock:

평균 응답시간 5ms

이 경우 테스트 결과가 실제 운영보다 빠르게 나타날 수 있다.

따라서 보고서에 다음을 기록한다.

* Mock 대상
* Mock 응답시간
* 실제 연계 여부
* 결과 해석의 제한사항

---

### 6. Load Generator의 한계를 시스템 한계로 오인하지 않는다.

목표 TPS가 나오지 않을 때 대상 서버만 확인하지 않는다.

예:

* WAS CPU: 30%
* DB 정상
* 실제 TPS 증가 정체
* Load Generator CPU: 100%

이라면 대상 시스템이 아니라 부하 생성기의 처리 한계일 수 있다.

따라서 최대부하 테스트에서는 Load Generator의 다음 항목도 함께 모니터링한다.

* CPU
* Memory
* Network
* Java Heap
* Thread
* 발생 가능한 최대 VUser

---

### 7. 순간값보다 추세를 본다.

다음과 같은 단일 순간값만으로 실패 또는 성공을 판단하지 않는다.

* 순간 CPU 90%
* 순간 최대 응답시간 5초
* 순간 최대 TPS 500

시간대별 그래프를 기준으로

* 얼마나 오래 지속되었는가?
* 반복적으로 발생하는가?
* 다른 지표와 동시에 변화했는가?

를 함께 확인한다.

---

### 8. 성능 비교는 동일 조건에서 수행한다.

개선 전후 결과를 비교하려면 가능한 한 다음 조건을 동일하게 유지한다.

* 테스트 시나리오
* 스크립트 버전
* VUser
* Think Time
* 업무 비율
* 테스트 데이터
* Ramp-up
* 서버 구성
* DB 구성
* 외부 연계
* 테스트 시간

조건이 다르면 성능 변화가 애플리케이션 개선 때문인지 테스트 조건 변화 때문인지 구분하기 어렵다.

---

### 9. 변경 사항을 기록한다.

테스트 차수마다 다음 변경사항을 기록한다.

예:

#### 1차

기본 설정

#### 2차

DB Index 추가

#### 3차

WAS 1대 추가

#### 4차

Connection Pool 100 → 200 변경

이를 기반으로 TPS, 응답시간, CPU 및 오류율의 변화를 비교한다.

성능검증은 단순 성공/실패 판정뿐 아니라 어떤 변경이 성능에 어떤 영향을 주었는지 확인하는 과정이다.

---

### 10. 병목은 요청 경로 전체에서 찾는다.

Performance Station 기반 성능검증에서는 다음 전체 요청 경로를 고려한다.

Load Generator
→ Network
→ Load Balancer
→ Web / WAS
→ Application
→ DB
→ 외부 연계
→ 응답 반환

특정 서버의 CPU만 확인하는 방식으로 병목을 판단하지 않는다.

---

## 핵심 판정 원칙

성능검증에서 다음 원칙을 공통 기준으로 사용한다.

VUser 증가 = TPS 증가를 보장하지 않는다.

TPS가 높다고 서비스 품질이 좋은 것은 아니다.

순간 최대 TPS를 시스템의 안정 처리량으로 판단하지 않는다.

CPU가 낮다고 시스템에 병목이 없다고 판단하지 않는다.

CPU 사용률만으로 증설 효과를 단순 계산하지 않는다.

WAS를 2배 증설했다고 TPS가 반드시 2배가 되는 것은 아니다.

평균 응답시간만으로 사용자 체감 성능을 판단하지 않는다.

검증계 한계를 운영계 한계로 단정하지 않는다.

Load Generator 한계를 대상 시스템의 한계로 오인하지 않는다.

근거 없는 단일 원인 확정은 하지 않는다.

성능검증은 최종적으로

목표 부하를 처리할 수 있는가

* 사용자가 충분히 빠르게 응답받는가
* 오류 없이 처리되는가
* 시스템 자원이 안정적인가
* 장시간에도 성능이 유지되는가
* 장애 상황에서도 서비스를 유지할 수 있는가

를 종합적으로 검증하는 과정이다.
