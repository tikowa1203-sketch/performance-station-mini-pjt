# 1. TPS(Transactions Per Second)

## TPS란?

TPS는 Transactions Per Second의 약자로, 시스템이 1초 동안 처리하는 Transaction의 수를 의미합니다.

쉽게 말하면 시스템이 초당 얼마나 많은 업무를 처리하고 있는지를 나타내는 성능지표입니다.

예:

100 TPS

→ 1초에 약 100개의 Transaction을 처리

500 TPS

→ 1초에 약 500개의 Transaction을 처리

TPS가 높을수록 일반적으로 더 많은 업무를 처리하고 있다는 의미입니다.

하지만 TPS가 높다고 해서 무조건 시스템 성능이 좋은 것은 아닙니다.

응답시간과 오류율을 함께 확인해야 합니다.

---

## Transaction이란?

TPS를 이해하기 위해서는 먼저 무엇을 하나의 Transaction으로 정의했는지 확인해야 합니다.

예를 들어 다음과 같은 사용자 업무가 있다고 가정합니다.

로그인
→ 고객조회
→ 계약조회
→ 로그아웃

Transaction을 어떻게 정의하느냐에 따라 TPS가 달라집니다.

### 정의 방법 A

각 API 요청을 Transaction으로 정의

* 로그인 = 1 Transaction
* 고객조회 = 1 Transaction
* 계약조회 = 1 Transaction
* 로그아웃 = 1 Transaction

한 명의 사용자가 한 번 업무를 수행하면 총 4개의 Transaction이 발생합니다.

### 정의 방법 B

전체 업무 흐름을 하나의 Transaction으로 정의

로그인 → 고객조회 → 계약조회 → 로그아웃

전체를 1 Transaction으로 볼 수도 있습니다.

따라서 서로 다른 시스템이나 테스트의 TPS를 비교할 때는 Transaction의 정의가 동일한지 먼저 확인해야 합니다.

---

# TPS 측정 방법

일반적으로 다음과 같이 계산할 수 있습니다.

TPS = 일정 시간 동안 처리한 Transaction 수 ÷ 시간(초)

예:

10초 동안 1,000건의 Transaction을 정상 처리했다면

1,000 ÷ 10 = 100 TPS

입니다.

---

## Performance Station에서 TPS 확인

Performance Station에서는 테스트 실행 중 또는 완료 후 다음 정보를 확인할 수 있습니다.

* 현재 TPS
* 평균 TPS
* 최대 TPS
* 시간대별 TPS
* 시나리오별 TPS
* 목표 TPS 대비 실제 TPS

예:

목표 TPS

104 TPS

실제 평균 TPS

108 TPS

이 경우 처리량 측면에서는 목표 TPS를 만족하고 있다고 볼 수 있습니다.

다만 다음 항목도 함께 확인해야 합니다.

* 응답시간
* 오류율
* CPU
* Memory
* DB
* 외부 연계 시스템

---

# TPS 해석 예

## 정상적인 경우

* 목표 TPS: 100
* 실제 TPS: 105
* 평균 응답시간: 0.8초
* 오류율: 0%
* CPU: 60%

→ 목표 부하를 안정적으로 처리하고 있다고 판단할 수 있습니다.

---

## 비정상적인 경우

* 목표 TPS: 100
* 실제 TPS: 110
* 평균 응답시간: 8초
* 오류율: 15%

TPS만 보면 목표를 만족하지만 실제 서비스 품질은 좋지 않습니다.

따라서 TPS는 반드시 응답시간과 오류율을 함께 확인해야 합니다.

# 2. VUser(Virtual User)

## VUser란?

VUser는 Virtual User, 즉 가상 사용자를 의미합니다.

성능테스트 도구가 실제 사용자 대신 시스템에 요청을 발생시키는 가상의 사용자입니다.

예:

100 VUser

→ 최대 100개의 가상 사용자 흐름이 동시에 실행

300 VUser

→ 최대 300개의 가상 사용자 흐름이 동시에 실행

---

# VUser와 실제 사용자 수는 같은가?

같지 않습니다.

가장 흔한 오해 중 하나가 다음과 같습니다.

300 VUser = 실제 사용자 300명

이라고 생각하는 것입니다.

실제 사용자는 서버에 계속 요청을 보내지 않습니다.

예를 들어 사용자는

로그인
→ 화면 확인
→ 20초 고민
→ 고객조회
→ 30초 확인
→ 계약조회

와 같은 방식으로 시스템을 사용합니다.

즉 실제 사용시간의 상당 부분은 서버에 요청을 보내지 않고 화면을 확인하거나 다음 행동을 생각하는 시간입니다.

따라서 실제 사용자 수와 동시에 요청을 발생시키는 VUser 수는 서로 다를 수 있습니다.

---

# VUser와 TPS의 관계

VUser를 증가시키면 일반적으로 TPS도 증가합니다.

예:

50 VUser

↓

100 TPS

100 VUser

↓

200 TPS

200 VUser

↓

400 TPS

하지만 항상 비례해서 증가하는 것은 아닙니다.

시스템의 처리 능력을 넘어가면 다음과 같은 현상이 나타날 수 있습니다.

VUser 증가

↓

TPS 증가

↓

시스템 임계점 도달

↓

VUser를 더 증가

↓

TPS는 증가하지 않음

↓

응답시간 증가

↓

오류 증가

---

## 예시

| VUser | TPS | 평균 응답시간 |
| ----: | --: | ------: |
|   100 | 100 |    0.5초 |
|   200 | 200 |    0.7초 |
|   300 | 300 |    0.9초 |
|   400 | 390 |    1.5초 |
|   500 | 400 |    4.5초 |
|   600 | 395 |    8.0초 |

500 VUser 이후에는 VUser를 증가시켜도 TPS가 거의 증가하지 않습니다.

오히려 응답시간만 크게 증가합니다.

이 경우 시스템이 처리 한계에 접근했다고 판단할 수 있습니다.

---

# VUser, 응답시간, Think Time, TPS의 관계

성능테스트에서는 네 가지 개념이 서로 연결되어 있습니다.

VUser
↕
응답시간
↕
Think Time
↕
TPS

개념적으로 반복되는 사용자 시나리오에서는 다음 관계를 이해하면 도움이 됩니다.

처리량 ≈ VUser ÷ (응답시간 + Think Time)

단, 실제 테스트에서는 하나의 시나리오에 여러 Transaction이 포함될 수 있기 때문에 정확한 TPS는 시나리오 구조와 Transaction 정의까지 함께 고려해야 합니다.

---

## 간단한 예

100명의 VUser가 있다고 가정합니다.

한 번의 업무를 수행하는 데

* 서버 응답시간: 2초
* Think Time: 8초

가 걸린다면 한 사용자가 한 번의 업무 사이클을 수행하는 데 약 10초가 필요합니다.

따라서 단순화하면

100명 ÷ 10초 = 약 10회/초

정도의 업무 흐름을 수행할 수 있습니다.

Think Time을 0초로 변경하면

100 ÷ 2초 = 약 50회/초

가 됩니다.

같은 100 VUser라도 Think Time에 따라 시스템에 발생하는 부하는 크게 달라집니다.

---

# 3. Think Time

## Think Time이란?

Think Time은 사용자가 하나의 작업을 수행한 후 다음 작업을 수행하기까지 기다리는 시간을 의미합니다.

실제 사람이 화면을 보고 생각하거나 입력하는 시간을 성능테스트에서 재현한 것입니다.

예:

고객조회

↓

화면 내용 확인

30초

↓

계약조회

여기서 30초가 Think Time입니다.

---

# Think Time이 필요한 이유

Think Time이 없으면 VUser는 응답을 받자마자 다음 요청을 보냅니다.

예:

로그인 → 즉시 고객조회 → 즉시 계약조회 → 즉시 상품조회 → 다시 반복

실제 사용자는 보통 이렇게 시스템을 사용하지 않습니다.

따라서 Think Time을 적절하게 적용해야 현실적인 사용자 환경을 재현할 수 있습니다.

---

# Think Time 설정 기준

Think Time은 가능하면 실제 사용자 행동을 기반으로 설정합니다.

활용할 수 있는 자료:

* 실제 운영 로그
* 사용자 행동 분석
* 업무 담당자 인터뷰
* 화면별 평균 체류시간
* 기존 성능테스트 기준
* 사용자 업무 분석

예:

| 업무            | 평균 Think Time |
| ------------- | ------------: |
| 로그인 후 메인화면 확인 |           10초 |
| 고객정보 확인       |           20초 |
| 계약정보 확인       |           30초 |
| 상품 비교         |           60초 |

---

# Think Time 0은 언제 사용하는가?

Think Time 0이 항상 잘못된 것은 아닙니다.

다음과 같은 테스트에서는 의도적으로 Think Time을 최소화할 수 있습니다.

* API 최대 처리량 측정
* 서버 임계점 확인
* Stress Test
* 단일 API 성능 측정

하지만 실제 사용자를 재현하는 기준 성능테스트에서는 적절한 Think Time을 설정하는 것이 좋습니다.

---

# VUser와 실제 사용자 규모

예를 들어 특정 서비스에서 분석 결과 다음과 같은 부하 모델을 사용한다고 가정합니다.

300 VUser + Think Time 30초

→ 약 3,000명 규모의 실제 사용자 활동을 재현

같은 모델에서

600 VUser + Think Time 30초

→ 약 6,000명 규모의 사용자 활동을 재현

이와 같은 환산은 해당 시스템의 사용자 행동 모델을 기반으로 만든 것입니다.

따라서

300 VUser = 무조건 실제 사용자 3,000명

이라는 범용 공식은 아닙니다.

다음 항목에 따라 환산값이 달라집니다.

* 업무 시나리오
* 업무별 요청 수
* 응답시간
* Think Time
* 사용자 행동 패턴
* Transaction 정의

---

# 4. 응답시간(Response Time)

## 응답시간이란?

응답시간은 사용자가 요청을 보낸 시점부터 시스템이 요청 처리를 완료하고 응답을 반환할 때까지 걸린 시간을 의미합니다.

예:

사용자 요청

10:00:00.000

시스템 응답

10:00:00.800

응답시간

0.8초

---

# 평균 응답시간

모든 요청의 응답시간을 더한 후 요청 수로 나눈 값입니다.

예:

응답시간:

* 0.5초
* 0.7초
* 0.8초
* 1.0초
* 2.0초

평균:

1.0초

평균 응답시간은 전체적인 성능 수준을 파악하는 데 유용합니다.

---

# 평균 응답시간의 한계

평균값만 보면 일부 사용자가 경험한 느린 응답이 가려질 수 있습니다.

예를 들어

100개의 요청 중

99개가 1초

1개가 30초

였다면 대부분 사용자는 정상적인 성능을 경험하지만 일부 사용자는 매우 느린 응답을 경험합니다.

따라서 평균값만으로 사용자 경험을 판단하지 않는 것이 좋습니다.

---

# P95 응답시간

P95는 95 Percentile을 의미합니다.

쉽게 설명하면

전체 요청의 약 95%가 이 시간 이하로 처리되었다

는 의미입니다.

예:

P95 = 2초

→ 전체 요청의 약 95%가 2초 이내에 처리됨

나머지 약 5%의 요청은 2초보다 느릴 수 있습니다.

---

# P95가 중요한 이유

평균 응답시간은 일부 매우 빠르거나 느린 요청에 영향을 받을 수 있습니다.

P95를 함께 보면 실제 사용자 대부분이 경험하는 응답시간을 보다 현실적으로 파악할 수 있습니다.

예:

### 테스트 A

* 평균: 0.8초
* P95: 1.2초
* 최대: 2초

### 테스트 B

* 평균: 0.8초
* P95: 4초
* 최대: 20초

두 테스트의 평균은 동일하지만 테스트 B에서 일부 사용자는 상당히 느린 응답을 경험하고 있습니다.

따라서 일반적으로 테스트 A가 더 안정적인 응답 특성을 보인다고 판단할 수 있습니다.

---

# 최대 응답시간

테스트 기간 중 가장 오래 걸린 요청의 응답시간입니다.

예:

* 평균: 0.8초
* P95: 1.5초
* 최대: 15초

최대값이 비정상적으로 크다면 어떤 요청에서 발생했는지 확인합니다.

가능한 원인:

* 일시적인 DB 지연
* GC
* Network 문제
* 외부 시스템 Timeout
* 특정 Query
* 최초 Cache Loading

---

# 평균 / P95 / 최대값을 함께 보는 방법

| 지표  | 의미                   |
| --- | -------------------- |
| 평균  | 전체적인 응답 수준           |
| P95 | 대부분의 사용자가 경험하는 응답 수준 |
| 최대  | 가장 느린 요청 또는 이상 구간 확인 |

세 가지를 함께 확인하는 것이 좋습니다.

---

# 응답시간 판정 기준

응답시간에 모든 시스템에 공통으로 적용되는 절대 기준이 있는 것은 아닙니다.

서비스의 특성과 사전에 정의한 성능 목표를 기준으로 판단해야 합니다.

예:

### 성능 목표

* 평균 응답시간: 1초 이하
* P95: 2초 이하
* 오류율: 1% 이하

### 결과

* 평균: 0.8초
* P95: 1.6초
* 오류율: 0.1%

→ 목표 기준 충족

---

# 응답시간 목표는 테스트 전에 정의하는 것이 중요

결과가 나온 후 기준을 만드는 것이 아니라 테스트 전에 목표를 정의하는 것이 좋습니다.

예:

목표

104 TPS 환경에서

* 평균 응답시간 1초 이하
* P95 2초 이하
* 오류율 1% 이하
* CPU 80% 이하

이후 테스트 결과를 이 기준과 비교합니다.

# 5. Throughput과 TPS

## Throughput이란?

Throughput은 일정 시간 동안 시스템이 처리한 전체 처리량을 의미하는 보다 넓은 개념입니다.

단위는 도구와 측정 대상에 따라 달라질 수 있습니다.

예:

* Requests/sec
* Transactions/sec
* Requests/min
* MB/sec
* 건/초
* 건/분

---

# TPS와 Throughput의 차이

TPS는 Throughput을 표현하는 한 가지 방식으로 볼 수 있습니다.

### TPS

Transaction / Second

초당 Transaction 처리량

### Throughput

일정 시간 동안 얼마나 많은 작업 또는 데이터를 처리했는지를 표현하는 보다 일반적인 개념

---

## 예

API 서버가 다음과 같이 요청을 처리한다고 가정합니다.

초당 HTTP 요청 500개

Performance Station 또는 JMeter에서는 이를

Throughput = 500 requests/sec

로 표현할 수 있습니다.

하지만 하나의 업무 Transaction이 HTTP 요청 5개로 구성되어 있다면 업무 기준으로는 단순히 500 TPS라고 부를 수 없습니다.

따라서 다음을 반드시 확인합니다.

Throughput이 무엇을 세고 있는가?

* HTTP Request인가?
* Transaction인가?
* 업무 시나리오인가?
* 데이터량인가?

---

# TPS 비교 시 주의사항

시스템 A

1 Transaction = HTTP 요청 1개

시스템 B

1 Transaction = HTTP 요청 10개

라면

단순히 두 시스템의 TPS 숫자만 비교하는 것은 의미가 없습니다.

Transaction 정의와 시나리오 구조를 먼저 확인해야 합니다.

---

# 6. 자원 사용률

성능테스트에서는 처리량과 응답시간뿐 아니라 서버의 자원 사용률을 함께 확인해야 합니다.

대표적인 자원 지표:

* CPU
* Memory
* Heap
* GC
* Thread
* Connection Pool
* DB Connection
* Disk I/O
* Network

---

# CPU 확인이 필요한 이유

CPU는 서버가 얼마나 많은 연산 작업을 수행하고 있는지를 파악하는 대표적인 지표입니다.

예:

### 낮은 부하

* TPS: 100
* CPU: 20%

### 높은 부하

* TPS: 400
* CPU: 70%

부하 증가에 따라 CPU도 증가한다면 어느 정도 자연스러운 패턴입니다.

---

# CPU 100%에 가까워지는 경우

CPU가 지속적으로 높은 상태를 유지한다면 처리 한계에 접근할 가능성이 있습니다.

예:

* CPU: 95%
* TPS 증가 정체
* 응답시간 증가

이 경우 CPU 병목 가능성을 검토합니다.

---

# CPU가 낮으면 성능에 문제가 없는가?

그렇지 않습니다.

다음과 같은 상황이 있을 수 있습니다.

* TPS 감소
* 응답시간 증가
* CPU 30%

이 경우 CPU가 아닌 다른 자원을 기다리고 있을 가능성이 있습니다.

예:

* DB 응답 대기
* 외부 API 대기
* Connection Pool 부족
* Thread 대기
* Lock
* Network 지연

따라서 CPU 하나만으로 시스템 상태를 판단하면 안 됩니다.

---

# Memory 확인이 필요한 이유

Memory는 특히 장시간 안정성 테스트에서 중요합니다.

정상적인 애플리케이션에서는 Memory가 사용되다가 GC에 의해 일정 부분 회수되는 패턴을 보일 수 있습니다.

예:

40%
→ 60%
→ GC
→ 42%
→ 60%
→ GC
→ 43%

비교적 안정적인 형태입니다.

---

# Memory Leak 의심 패턴

다음과 같이 GC 이후에도 Memory 기준점이 계속 상승한다면 추가 분석이 필요합니다.

40%
→ 60%
→ GC
→ 50%
→ 70%
→ GC
→ 60%
→ 80%

Memory가 장시간 지속적으로 증가한다면

* Memory Leak
* Object 미회수
* Cache 증가
* Session 누적

등을 확인할 수 있습니다.

---

# CPU와 Memory 외에 확인해야 하는 지표

## WAS

* CPU
* Memory
* Heap
* GC
* Thread
* Connection Pool

## DB

* CPU
* Active Session
* Connection
* Query 응답시간
* Lock
* Wait

## Network

* Traffic
* Connection
* Packet Error
* Network Latency

## 외부 시스템

* 응답시간
* 오류율
* Timeout

---

# 성능지표는 서로 연결되어 있다

성능테스트에서 가장 중요한 원칙은 하나의 지표만 독립적으로 보지 않는 것입니다.

예를 들어 다음과 같은 흐름을 확인해야 합니다.

VUser 증가

↓

TPS 증가

↓

CPU 증가

↓

응답시간 증가

↓

어느 시점부터

VUser 증가

↓

TPS 정체

↓

응답시간 급증

↓

Error 증가

이러한 흐름을 통해 시스템의 처리 한계와 병목 발생 시점을 찾을 수 있습니다.

---

# 주요 지표 관계 예시

## 정상 상태

* VUser: 일정
* TPS: 일정
* 응답시간: 일정
* Error: 낮음
* CPU: 안정
* Memory: 안정

판단:

안정적인 처리 상태

---

## CPU 병목 가능성

* VUser 증가
* TPS 증가
* CPU 지속 증가
* CPU 90~100%
* TPS 증가 정체
* 응답시간 급증

판단:

CPU 처리 한계 가능성

---

## DB 또는 외부 시스템 병목 가능성

* VUser 증가
* TPS 정체
* 응답시간 증가
* WAS CPU 낮음
* DB 또는 외부 시스템 응답시간 증가

판단:

WAS보다 DB 또는 외부 시스템 병목 가능성

---

## Load Generator 병목 가능성

성능테스트에서는 대상 시스템뿐 아니라 부하를 발생시키는 Load Generator도 확인해야 합니다.

예:

* 대상 WAS CPU: 30%
* TPS 증가 안 됨
* Load Generator CPU: 100%

이 경우 대상 시스템이 아니라 부하발생기의 한계 때문에 충분한 부하를 만들지 못하고 있을 가능성이 있습니다.

---

# 실무 예제

다음과 같은 테스트 결과가 있다고 가정합니다.

## 목표

* 목표 TPS: 104 TPS
* 평균 응답시간: 1초 이하
* CPU: 80% 이하
* Error: 1% 이하

## 결과

* 평균 TPS: 110 TPS
* 평균 응답시간: 0.8초
* P95: 1.3초
* 최대 응답시간: 2.75초
* Error: 0%
* WAS 평균 CPU: 42%

### 해석

목표 TPS인 104 TPS 이상을 안정적으로 처리했습니다.

평균 응답시간도 목표인 1초 이하이며 P95와 오류율에서도 특이사항이 없습니다.

WAS CPU 사용률도 약 42%로 확인되어 해당 부하 수준에서 서버 자원에 여유가 있는 것으로 볼 수 있습니다.

따라서 설정된 테스트 환경과 범위 안에서는 목표 성능을 충족한 것으로 판단할 수 있습니다.

다만 더 높은 부하에서 어느 수준까지 성능이 확장되는지는 최대부하 테스트를 통해 별도로 확인해야 합니다.

---

# 주의사항

# 1. VUser를 실제 사용자 수로 오해하지 않습니다.

잘못된 해석:

300 VUser니까 실제 사용자 300명을 테스트했다.

올바른 해석:

VUser는 동시에 실행되는 가상 사용자이며 실제 사용자 규모는 업무 패턴, Think Time, 응답시간 등을 고려하여 산정해야 합니다.

---

# 2. VUser와 TPS를 동일하게 생각하지 않습니다.

잘못된 해석:

100 VUser = 100 TPS

VUser와 TPS는 서로 다른 개념입니다.

TPS는 다음 요소의 영향을 받습니다.

* VUser
* 응답시간
* Think Time
* 시나리오 구조
* Transaction 수
* 시스템 처리능력

---

# 3. TPS가 높으면 무조건 성능이 좋다고 판단하지 않습니다.

예:

* TPS: 높음
* 응답시간: 10초
* Error: 20%

이런 시스템은 정상적인 서비스라고 보기 어렵습니다.

TPS는 반드시 응답시간과 오류율을 함께 확인합니다.

---

# 4. 순간 최대 TPS를 시스템 최대 성능이라고 판단하지 않습니다.

테스트 중 순간적으로 500 TPS가 나타났다고 해서

시스템 최대 성능 = 500 TPS

라고 바로 판단하면 안 됩니다.

안정적인 최대 처리량은 일정 시간 동안 다음이 유지되는지를 확인해야 합니다.

* TPS
* 응답시간
* 오류율
* CPU / Memory
* 시스템 안정성

---

# 5. 평균 응답시간만 확인하지 않습니다.

평균값은 일부 느린 요청을 숨길 수 있습니다.

가능하면 다음을 함께 확인합니다.

* 평균
* P95
* P99
* 최대
* 시간대별 응답시간

---

# 6. 최대 응답시간 한 건만으로 전체 성능이 나쁘다고 단정하지 않습니다.

최대 응답시간이 20초라고 해도 한 건의 일시적인 현상일 수 있습니다.

다음 항목을 함께 확인합니다.

* 발생 빈도
* P95 / P99
* 발생 시간
* 해당 Transaction
* 서버 상태

반대로 최대값 한 건이라고 무조건 무시해서도 안 됩니다.

---

# 7. CPU 50%를 성능 여유 50%라고 생각하지 않습니다.

잘못된 해석:

CPU가 50%니까 TPS를 두 배까지 올릴 수 있다.

CPU와 TPS가 항상 선형 관계를 가지는 것은 아닙니다.

병목은 다음에서 먼저 발생할 수 있습니다.

* DB
* Connection Pool
* Thread
* Network
* 외부 연계
* 인증 시스템

---

# 8. 서버 수와 TPS를 단순 비례시키지 않습니다.

잘못된 해석:

WAS 1대에서 500 TPS

↓

WAS 2대면 무조건 1,000 TPS

시스템이 완벽하게 수평 확장되는 경우에는 TPS 증가를 기대할 수 있지만 실제 시스템에서는 다음 공유 자원이 병목이 될 수 있습니다.

* DB
* Cache
* 외부 시스템
* Network
* 인증 서버
* Shared Storage

따라서 서버 증설 효과는 실제 테스트로 검증해야 합니다.

---

# 9. Think Time을 줄인 결과를 성능 개선으로 오해하지 않습니다.

예:

### 테스트 A

* 300 VUser
* Think Time 30초
* 100 TPS

### 테스트 B

* 300 VUser
* Think Time 5초
* 300 TPS

테스트 B의 TPS가 높아졌다고 해서 시스템 성능이 세 배 개선된 것은 아닙니다.

부하 조건 자체가 달라진 것입니다.

---

# 10. 다른 조건의 테스트를 단순 비교하지 않습니다.

두 테스트의 TPS나 응답시간을 비교하려면 다음 조건을 확인해야 합니다.

* VUser
* Think Time
* 시나리오
* 스크립트 버전
* 업무 비율
* 테스트 데이터
* 서버 구성
* DB 구성
* 테스트 환경

조건이 다르면 수치 차이가 시스템 성능 변화 때문인지 테스트 조건 때문인지 구분하기 어렵습니다.

# 성능테스트 결과를 보는 기본 순서

성능테스트를 처음 접하는 사용자는 다음 순서로 지표를 확인하는 것이 좋습니다.

① VUser 확인
→ ② Think Time 확인
→ ③ 목표 TPS 확인
→ ④ 실제 TPS 확인
→ ⑤ 평균/P95 응답시간 확인
→ ⑥ 오류율 확인
→ ⑦ CPU 확인
→ ⑧ Memory 확인
→ ⑨ DB 및 외부 연계 확인
→ ⑩ 동일 시간대의 지표를 종합하여 판단

성능테스트의 핵심은 특정 숫자 하나를 보는 것이 아니라 부하가 증가하거나 시간이 지나면서 여러 지표가 어떤 관계로 변화하는지를 분석하는 것입니다.

---

# 반드시 기억할 핵심 원칙

VUser ≠ 실제 사용자 수

VUser ≠ TPS

TPS가 높음 ≠ 성능이 무조건 좋음

CPU가 낮음 ≠ 병목이 없음

CPU 50% ≠ 성능 여유 50%

순간 최대 TPS ≠ 안정적인 최대 처리성능

평균 응답시간 정상 ≠ 모든 사용자의 응답시간 정상

WAS 2대 ≠ WAS 1대 성능의 정확히 2배

성능은 하나의 숫자가 아니라

처리량 + 응답시간 + 오류율 + 자원 사용률 + 시간에 따른 변화

를 함께 분석하여 판단합니다.
