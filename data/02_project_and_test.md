# 02. 프로젝트와 테스트 생성

## 적용 화면 또는 기능

본 문서는 Performance Station에서 성능테스트를 수행하기 위한 기본 관리 단위인 프로젝트(Project) 와 테스트(Test) 을 생성하고 관리하는 방법을 설명합니다.

주요 적용 화면 및 기능은 다음과 같습니다.

* 프로젝트 목록 화면
* 프로젝트 생성 화면
* 프로젝트 상세정보 화면
* 프로젝트 수정 화면
* 테스트 목록 화면
* 테스트 생성 화면
* 테스트 상세정보 화면
* 테스트 수정/삭제 기능

Performance Station에서는 일반적으로 다음과 같은 구조로 성능테스트를 관리합니다.

프로젝트(Project)
└ 테스트(Test)
　└ 시나리오(Scenario)
　　└ 부하 조건(Load)
　　　└ 테스트 실행
　　　　└ 결과(Result)

하나의 프로젝트에는 여러 개의 테스트를 생성할 수 있으며, 테스트 목적에 따라 기준성능, 최대부하, 안정성, 가용성 등의 테스트를 구분하여 관리할 수 있습니다.

---

## 사전 조건

### 1. 프로젝트 생성 권한

프로젝트를 생성하려면 프로젝트 생성 권한이 있는 사용자 계정이 필요합니다.

일반적으로 다음 사용자가 프로젝트를 생성할 수 있습니다.

* 시스템 관리자
* 프로젝트 관리자
* 성능테스트 담당자
* 프로젝트 생성 권한이 별도로 부여된 사용자

일반 조회 권한만 가진 사용자는 프로젝트를 조회할 수 있지만 생성이나 수정이 제한될 수 있습니다.

프로젝트 생성 버튼이 표시되지 않거나 비활성화된 경우 사용자 권한을 먼저 확인합니다.

---

### 2. 프로젝트 생성 시 필요한 정보

프로젝트 생성 시 일반적으로 다음 정보를 입력합니다.

#### 필수 또는 주요 입력 항목

* 프로젝트명
* 대상 시스템 또는 서비스명
* 프로젝트 설명
* 프로젝트 담당자
* 프로젝트 수행 기간
* 참여 사용자
* 대상 환경

예:

* 프로젝트명: 영업지원시스템 성능검증
* 대상 시스템: 영업지원시스템
* 담당자: 성능검증 담당자
* 대상 환경: 검증계
* 수행 목적: 신규 시스템 오픈 전 성능검증

실제 필수 입력 항목은 Performance Station 버전이나 운영 정책에 따라 달라질 수 있습니다.

---

### 3. 테스트 생성 권한

테스트를 생성하려면 다음 조건을 만족해야 합니다.

* 프로젝트 접근 권한 보유
* 해당 프로젝트의 테스트 생성 권한 보유
* 정상 상태의 프로젝트
* 프로젝트 기본정보 등록 완료

프로젝트는 조회되지만 테스트 생성 버튼이 활성화되지 않는 경우 프로젝트별 사용자 권한을 확인합니다.

---

# 단계별 절차

## 1. 프로젝트 생성

### STEP 1. 프로젝트 메뉴 이동

Performance Station에 로그인한 후 메인 화면에서 프로젝트 또는 프로젝트 관리 메뉴로 이동합니다.

사용자가 접근 가능한 기존 프로젝트 목록이 표시됩니다.

---

### STEP 2. 신규 프로젝트 생성

프로젝트 목록 화면에서 프로젝트 생성, 신규 프로젝트, + 프로젝트 등의 버튼을 선택합니다.

프로젝트 생성 화면이 표시됩니다.

---

### STEP 3. 프로젝트 기본정보 입력

프로젝트에 필요한 기본정보를 입력합니다.

예:

프로젝트명

영업지원시스템 성능검증

대상 시스템

영업지원시스템

테스트 환경

검증계

프로젝트 목적

영업지원시스템 오픈 전 목표 성능 및 최대 처리 성능 검증

수행 기간

2026.09.01 ~ 2026.09.30

담당자

성능검증 담당자

---

### STEP 4. 참여 사용자 등록

프로젝트를 함께 수행할 사용자를 등록합니다.

필요한 경우 사용자별로 다음과 같은 권한을 부여할 수 있습니다.

* 프로젝트 관리자
* 테스트 생성/수정
* 테스트 실행
* 결과 조회
* 조회 전용

프로젝트 참여자가 등록되지 않으면 해당 사용자의 프로젝트 목록에서 프로젝트가 보이지 않을 수 있습니다.

---

### STEP 5. 프로젝트 저장

입력한 정보를 확인한 후 저장 또는 생성 버튼을 선택합니다.

프로젝트 생성이 완료되면 프로젝트 목록에 신규 프로젝트가 표시됩니다.

프로젝트를 선택하면 프로젝트 상세 화면으로 이동하며 해당 프로젝트의 테스트를 생성할 수 있습니다.

---

# 2. 프로젝트 정보 수정

프로젝트 생성 이후 프로젝트명, 담당자, 기간 등의 기본정보를 수정할 수 있습니다.

### 수정 절차

1. 프로젝트 목록으로 이동합니다.
2. 수정할 프로젝트를 선택합니다.
3. 프로젝트 상세 화면으로 이동합니다.
4. 수정 또는 프로젝트 정보 수정을 선택합니다.
5. 필요한 항목을 변경합니다.
6. 변경 내용을 저장합니다.

일반적으로 다음 항목을 수정할 수 있습니다.

* 프로젝트명
* 프로젝트 설명
* 수행 기간
* 담당자
* 참여 사용자
* 대상 시스템 정보

---

### 프로젝트 수정 시 확인사항

이미 테스트가 진행 중이거나 완료된 프로젝트의 경우 일부 정보는 수정이 제한될 수 있습니다.

특히 프로젝트명을 변경하면 기존 테스트 결과 또는 보고서에서 사용하는 명칭과 달라질 수 있으므로 주의합니다.

가능하면 프로젝트 생성 시 명확한 명명 규칙을 사용하는 것을 권장합니다.

---

# 3. 테스트 생성

프로젝트가 생성되면 실제 성능검증을 수행하기 위한 테스트를 생성합니다.

프로젝트 하나에는 여러 테스트를 생성할 수 있습니다.

예:

영업지원시스템 성능검증

* 단위 성능테스트
* 기준 성능테스트
* 최대부하 테스트
* 안정성 테스트
* 가용성 테스트

---

## STEP 1. 프로젝트 선택

프로젝트 목록에서 테스트를 생성할 프로젝트를 선택합니다.

프로젝트 상세 화면에서 테스트, 테스트관리, Test 등의 메뉴로 이동합니다.

---

## STEP 2. 신규 테스트 생성

테스트 목록 화면에서 테스트 생성, 신규 테스트, + 테스트 버튼을 선택합니다.

테스트 생성 화면에서 테스트 정보를 입력합니다.

---

## STEP 3. 테스트명 입력

테스트 목적을 쉽게 확인할 수 있도록 테스트명을 작성합니다.

좋은 예:

* 기준성능_1차
* 최대부하_1차
* 안정성_8시간
* 가용성_WAS장애전환
* 통합인증_최대부하

피해야 할 예:

* test1
* 테스트
* 신규테스트
* 테스트최종
* 최종진짜최종

테스트명만 보고도 무엇을 검증하는 테스트인지 알 수 있도록 작성하는 것이 중요합니다.

---

## STEP 4. 테스트 유형 선택

테스트 목적에 따라 테스트 유형을 선택합니다.

Performance Station에서는 프로젝트 목적에 따라 다음과 같은 성능테스트를 수행할 수 있습니다.

### 단위 성능테스트

특정 업무 또는 API 단위의 성능을 확인하는 테스트입니다.

주로 하나의 시나리오 또는 특정 기능에 대해 응답시간과 처리 성능을 확인합니다.

예:

* 로그인 API 성능
* 고객조회 성능
* 계약조회 성능

---

### 기준 성능테스트

서비스의 정상적인 예상 사용자 부하를 적용하여 목표 성능을 만족하는지 확인합니다.

주요 확인 항목:

* 목표 TPS
* 평균 응답시간
* 오류율
* CPU 사용률
* Memory 사용률

예:

목표 104 TPS 환경에서 정상적으로 서비스가 처리되는지 확인합니다.

---

### 최대부하 테스트

부하를 단계적으로 증가시켜 시스템이 안정적으로 처리할 수 있는 최대 성능을 확인합니다.

일반적으로 다음과 같이 부하를 증가시킵니다.

100 TPS
→ 200 TPS
→ 300 TPS
→ 400 TPS
→ 시스템 임계점 확인

최대부하 테스트에서는 단순히 서버 CPU 사용률만 확인하기보다 다음 요소를 함께 분석합니다.

* WAS
* DB
* 외부 연계 시스템
* 네트워크
* 인증 시스템
* Connection Pool
* Thread Pool

---

### 안정성 테스트

일정한 부하를 장시간 유지하여 시스템의 안정성을 확인합니다.

예:

* 목표 부하 70%
* 테스트 시간 8시간

주요 확인 항목:

* Memory 증가 여부
* Memory Leak
* 응답시간 증가 추세
* Error 증가
* Connection 누수
* CPU 사용률 변화
* 장시간 처리 안정성

---

### 가용성 테스트

서버 장애 또는 일부 시스템 장애 상황에서도 서비스가 정상적으로 유지되는지 확인합니다.

예:

WAS 2대 구성

WAS1 + WAS2 정상 서비스

↓

WAS1 중단

↓

WAS2 서비스 처리 확인

↓

WAS1 복구

↓

서비스 정상화 확인

주요 확인 항목:

* 장애 발생 시 서비스 중단 여부
* L4 또는 Load Balancer 전환
* 응답시간 변화
* TPS 변화
* 세션 유지 여부
* 장애 서버 복구 이후 영향

---

## STEP 5. 테스트 기본정보 입력

테스트 유형을 선택한 후 테스트에 필요한 정보를 입력합니다.

주요 항목은 다음과 같습니다.

* 테스트명
* 테스트 유형
* 테스트 목적
* 테스트 설명
* 테스트 대상 시스템
* 테스트 환경
* 테스트 담당자
* 테스트 일정

예:

테스트명

영업지원_기준성능_1차

테스트 유형

기준 성능테스트

테스트 목적

목표 104 TPS 환경에서 응답시간 및 서버 자원 사용률 확인

대상 환경

검증계

---

## STEP 6. 테스트 저장

입력한 내용을 확인하고 저장 또는 테스트 생성 버튼을 선택합니다.

테스트가 생성되면 테스트 목록에 신규 테스트가 표시됩니다.

테스트를 선택하면 이후 다음 작업을 수행할 수 있습니다.

테스트 생성
→ 시나리오 등록
→ 부하 조건 설정
→ 테스트 실행
→ 결과 확인

---

# 4. 테스트 정보 수정

테스트 생성 후 테스트 실행 전이라면 대부분의 테스트 정보를 수정할 수 있습니다.

### 수정 절차

1. 프로젝트를 선택합니다.
2. 테스트 목록으로 이동합니다.
3. 수정할 테스트를 선택합니다.
4. 테스트 정보 수정을 선택합니다.
5. 필요한 항목을 변경합니다.
6. 변경 내용을 저장합니다.

수정 가능한 항목의 예:

* 테스트명
* 테스트 설명
* 테스트 유형
* 테스트 일정
* 테스트 담당자
* 테스트 목적

---

## 테스트 실행 이후 수정

테스트가 이미 실행된 경우 테스트 결과의 정합성을 위해 일부 항목의 수정이 제한될 수 있습니다.

특히 다음 항목은 테스트 실행 후 변경 시 주의합니다.

* 테스트 유형
* 테스트명
* 시나리오
* Virtual User
* 목표 TPS
* 테스트 시간

테스트 조건을 변경해야 하는 경우 기존 테스트를 수정하기보다 새로운 차수의 테스트를 생성하는 방식을 권장합니다.

예:

기존

최대부하_1차

조건 변경 후

최대부하_2차

이렇게 관리하면 테스트 조건과 결과를 비교하기 쉽습니다.

---

# 5. 테스트 삭제

테스트가 불필요한 경우 권한이 있는 사용자는 테스트를 삭제할 수 있습니다.

일반적인 삭제 절차는 다음과 같습니다.

1. 프로젝트 선택
2. 테스트 목록 이동
3. 삭제 대상 테스트 선택
4. 삭제 버튼 선택
5. 삭제 확인
6. 테스트 삭제

---

## 테스트 삭제 전 반드시 확인

테스트를 삭제하면 다음 데이터가 함께 삭제될 수 있습니다.

* 테스트 기본정보
* 시나리오 설정
* 부하 설정
* 테스트 실행 이력
* 성능 측정 결과
* 테스트 결과 리포트

따라서 이미 실행한 테스트는 가급적 삭제하지 않는 것을 권장합니다.

잘못 생성한 테스트라도 테스트 이력이 존재하는 경우 다음과 같이 관리하는 것이 안전합니다.

예:

상태: 사용 중지

또는

테스트명: [미사용] 최대부하_테스트

---

# 프로젝트 및 테스트 명명 규칙

프로젝트와 테스트가 많아지면 이름만 보고 테스트 내용을 구분하기 어려워질 수 있습니다.

따라서 일정한 명명 규칙을 사용하는 것이 좋습니다.

## 프로젝트명 권장 규칙

시스템명 + 목적

예:

* 영업지원시스템_성능검증
* 통합인증_성능검증
* 모바일앱_성능테스트
* 차세대시스템_오픈전성능검증

---

## 테스트명 권장 규칙

테스트유형 + 차수

또는

업무명 + 테스트유형 + 차수

예:

* 기준성능_1차
* 기준성능_2차
* 최대부하_1차
* 안정성_8시간_1차
* 가용성_WAS장애_1차
* 로그인_단위성능_1차
* 영업지원_최대부하_2차

날짜를 포함하여 관리할 수도 있습니다.

예:

영업지원_최대부하_20260903_1차

---

# 주의사항

## 프로젝트를 너무 세분화하지 않습니다.

테스트마다 프로젝트를 새로 만들기보다는 동일한 시스템의 성능테스트는 하나의 프로젝트에서 관리하는 것이 좋습니다.

권장 구조:

영업지원시스템 성능검증

* 기준성능
* 최대부하
* 안정성
* 가용성

비권장 구조:

* 영업지원 기준성능 프로젝트
* 영업지원 최대부하 프로젝트
* 영업지원 안정성 프로젝트
* 영업지원 가용성 프로젝트

동일한 시스템의 테스트를 하나의 프로젝트에서 관리하면 테스트 이력과 결과를 비교하기 쉽습니다.

---

## 테스트 목적을 반드시 작성합니다.

테스트 이름만 등록하지 않고 테스트 목적을 함께 작성하는 것이 좋습니다.

예:

테스트 목적

운영 예상 Peak 부하인 104 TPS를 적용하여 평균 응답시간 1초 이내 및 서버 CPU 80% 이하 여부를 확인한다.

테스트 목적이 명확하면 결과 분석 단계에서 성공/실패 기준을 판단하기 쉽습니다.

---

## 테스트 조건 변경 시 기존 결과를 덮어쓰지 않습니다.

테스트 조건이 변경된 경우 기존 테스트를 수정하여 다시 실행하기보다 새로운 테스트 또는 새로운 차수를 생성하는 것이 좋습니다.

예:

기준성능_1차

↓

시나리오 또는 부하 조건 변경

↓

기준성능_2차

이렇게 관리하면 변경 전후 성능을 비교할 수 있습니다.

---

## 테스트 유형을 정확하게 선택합니다.

테스트 유형을 잘못 선택하면 이후 결과 분석 또는 리포트 분류가 어려울 수 있습니다.

테스트 생성 전에 반드시 테스트 목적을 먼저 확인합니다.

* 특정 업무 성능 확인 → 단위 성능테스트
* 목표 부하 검증 → 기준 성능테스트
* 최대 처리 성능 확인 → 최대부하 테스트
* 장시간 운영 확인 → 안정성 테스트
* 장애 상황 서비스 유지 확인 → 가용성 테스트

---

## 프로젝트 및 테스트 삭제는 신중하게 수행합니다.

프로젝트 또는 테스트 삭제 시 관련 테스트 결과까지 함께 삭제될 수 있습니다.

특히 완료된 성능테스트의 경우 향후 다음 목적으로 활용될 수 있습니다.

* 성능 비교
* 장애 분석
* 시스템 증설 검토
* 운영 성능 기준 수립
* 성능검증 보고서 작성

따라서 완료된 테스트는 가능하면 삭제하지 않고 이력으로 관리합니다.

# 자주 발생하는 문제

## 프로젝트 생성 버튼이 보이지 않습니다.

가능한 원인

프로젝트 생성 권한이 없는 사용자일 수 있습니다.

조치

시스템 관리자에게 프로젝트 생성 권한을 요청합니다.

---

## 테스트 생성 버튼이 비활성화되어 있습니다.

가능한 원인

* 프로젝트 접근 권한 부족
* 테스트 생성 권한 부족
* 프로젝트 상태가 종료됨
* 프로젝트 기본정보 미등록

조치

프로젝트 상태와 사용자 권한을 확인합니다.

---

## 생성한 프로젝트가 다른 사용자에게 보이지 않습니다.

가능한 원인

해당 사용자가 프로젝트 참여자로 등록되지 않았거나 프로젝트 접근 권한이 부여되지 않았을 수 있습니다.

조치

프로젝트 사용자 또는 권한 관리 화면에서 대상 사용자를 등록합니다.

---

## 테스트 조건을 잘못 설정했습니다.

테스트 실행 전이라면 테스트 정보를 수정합니다.

이미 테스트를 실행했다면 기존 테스트 결과를 유지하고 새로운 차수의 테스트를 생성하는 것을 권장합니다.

예:

최대부하_1차

↓

조건 수정

↓

최대부하_2차

---

# 프로젝트와 테스트 생성 권장 흐름

Performance Station에서 새로운 성능검증을 시작할 경우 다음 순서로 진행합니다.

① 대상 시스템 확인
→ ② 프로젝트 생성
→ ③ 프로젝트 담당자/사용자 등록
→ ④ 테스트 목적 정의
→ ⑤ 테스트 유형 선택
→ ⑥ 테스트 생성
→ ⑦ 시나리오 등록
→ ⑧ 부하 조건 설정
→ ⑨ 테스트 실행
→ ⑩ 결과 분석

특히 테스트를 생성하기 전에 무엇을 검증하기 위한 테스트인지 먼저 정의하는 것이 중요합니다.

테스트 목적이 명확해야 적절한 테스트 유형, 시나리오, 부하 조건 및 성공 기준을 설정할 수 있습니다.
